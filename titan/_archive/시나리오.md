## 4. #4-4 — UGV 이동 명령 + 아군 동반 기동

**시작 조건**: UGV 이동 명령 수신(좌표 + 반경).

**진행**:
1. UGV 목표 위치(적과의 교전 거리를 고려해서 정한 좌표)를 미니맵에 마커 추가.
   **이 목표 좌표는 언리얼 에디터에서 사용자가 직접 조정 가능한 값으로 구현** —
   같은 패턴("특정 위치로 자연스럽게 이동"을 에디터에서 커스텀 가능하게)을
   나중에 적군이 교전 위치로 이동하는 로직 등에도 재사용할 예정.
2. UGV가 경로 자동 생성(또는 사전 지정 경로) 후 주행 시작 — 기존
   `UGVAIController` 자동주행 그대로.
3. **UGV가 움직이기 시작하는 순간부터 곧바로 아군도 뛰어서(달리기 애니메이션)
   동반 이동 시작** — 별도의 "아군 이동 시작" 트리거 없음, UGV 자동주행에
   아군이 붙어가는 구조.
4. **대형 확정**: 앞15/뒤15(좌우 없이 선발조-UGV-후발조 한 줄). 선발조/후발조와
   UGV 사이 간격은 에디터에서 사용자가 조정 가능한 값으로. **아군끼리 서로
   겹치지 않게** 각자 대형 내 슬롯 사이 최소 간격을 두는 처리 필요.
5. UGV 통제기 조이스틱으로는 RCWS 각도만 조작 가능(주행은 자동, UGV에는
   4방향 카메라가 없으므로 그쪽 화면은 없음).
6. **UGV 속도 제어**: 자동주행 시 최대 속도를 사용자가 커스텀 가능한 값으로
   설정하고, 실제로 그 속도를 넘지 않도록 액셀/브레이크를 상황에 맞게 사용하는
   로직 필요 — 최대 기어 제한만으로는 내리막길에서 속도 초과를 막을 수 없음
   (기어 제한은 상한 회전수만 건드릴 뿐, 내리막에서는 중력이 그 이상으로
   가속시킬 수 있음).
7. **충돌 회피**: 아군과 UGV가 서로 부딪히지 않도록(특히 선발조가 UGV 앞에서
   너무 느려지거나 후발조가 UGV에 따라잡히는 경우 등) 로직을 신경써서 구현
   필요.

**소요시간**: `[제안]` 목적지까지 거리에 따라 유동적. 아군이 UGV와 같은 속도를
유지하도록 UGV와의 거리를 보고 스스로 속도를 맞추는 로직 필요.

## 5. #4-5 — UGV 접근 완료, 아군 매복 위치 전환, 적군 식별

**시작 조건**: UGV가 목표 지점 반경 **20m** 이내 진입.

**진행**:
1. UGV가 20m 반경에 들어오는 순간, **아군 전원이 동시에** "UGV를 따라가기"
   목표를 버리고 각자 **자신의 매복(엄폐) 지점**으로 목표를 전환 — 이때부터는
   전력 질주가 아니라 **천천히 이동하면서 경계 자세**(주변을 살피는 느낌)를
   취함.
   ++ ugv 20m 반경 도착 시 분대장 역할의 선두 아군 한명(ugv rcws 가 잘 보이는 위치로 세팅할 예정)이 수신호로 아군들에게 수신호로 산개하라는 듯한 명령 전달, 이후 아군들이 자연스럽게 목표 전환 후 이동하는 연출.
   - **시간 제약**: 이후 6절의 매복 트리거(적 포착)가 발생하면, 이미 매복
     지점에 도착해서 "빠르게 엄폐 + 사격 준비"로 넘어갈 수 있어야 함 — 즉
     20m 지점부터 매복 지점 도착까지 걸리는 시간이, 다음 트리거가 발생하기
     전에 충분히 끝나야 함. 구체적인 초 단위 여유는 실측/튜닝 필요(11절 계속
     열려있음).
   - **폴백 확정**: 적 포착 트리거가 발생했는데 아직 매복 지점에 도착하지
     못한 아군이 있으면, 그 아군만 "빠르게 뛰어서" 매복 지점까지 마저 이동 —
     좋은 방향. 타이밍이 딱 안 맞아도 자연스럽게 커버되는 폴백이라 굳이
     타이트하게 튜닝할 필요가 없어짐(위 "몇 초 여유" 질문도 사실상 이걸로
     해소됨 — 늦으면 뛰면 되니까).
2. UGV는 목표 지점 반경 10m 이내에서 완전 정지(기존 도착 판정 그대로 유지).
3. UGV RCWS 화면에 보이는 적군만큼만 적색 바운딩 박스 표시 — **전원이 한 번에
   보일 필요 없음**. 적군은 계속 자연스럽게 걸어오는 중이라 나무 등 지형에
   가려서 안 보이다가, 아군이 경계 중인 지점 시야로 하나둘 들어오는 개념
   (기존 `TargetDetectionComponent`의 시야/오클루전 판정을 그대로 쓰면 됨 —
   "전원 노출"을 인위적으로 만들 필요가 없다는 뜻).

## 12. 시나리오를 어떤 형태로 저장/재생할지 — 시퀀서 vs 데이터 에셋

**결론부터: 시퀀서보다는 `DataTable`(또는 `DataAsset`) 쪽을 권장.**

- **시퀀서(Level Sequencer)**는 카메라 컷/트랙 애니메이션처럼 "정해진 시간에
  정해진 일이 일어나는" **타임라인 연출**에 최적화된 도구야. 지금 우리
  시나리오는 시간보다 **조건**(거리 30m 이내, RCWS가 적을 포착했는지 등)으로
  다음 단계가 결정되는 비중이 커서, 시퀀서로 하려면 이벤트 트랙에 Blueprint
  조건 분기를 억지로 끼워넣어야 함 — 되긴 하지만 이 프로젝트 성격엔 안 맞음.
  다만 **특정 구간의 순수 카메라 연출(컷씬 느낌)만 부분적으로 시퀀서를 쓰는
  건 나중에 고려 가능** — 시나리오 로직의 메인 드라이버로는 비권장.
- **`DataTable`** (C++로 한 행의 구조체만 정의하면 언리얼 에디터에서 엑셀 같은
  표로 편집 가능, 재컴파일 없이 값 수정): 각 단계(#4-1~#4-8)를 한 행으로 —
  이름, 시작 조건 타입(이벤트/거리/타이머 등 enum), 조건 파라미터, 대기시간,
  효과 종류 같은 컬럼으로 구성. **사용자가 원한 "커스텀하기 편함"에 가장
  가까움** — 표에서 숫자만 바꾸면 됨, 코드 수정도 재빌드도 필요 없음. MCP의
  `DataTableTools`로 다루기도 좋음.
- 지금 있는 `UScenarioStateSubsystem`(현재는 #4-1만 흉내내는 최소 코드)을
  이 `DataTable`을 읽어서 단계를 순서대로 진행시키는 매니저로 확장하는 걸
  제안 — 완전히 새로 만들지 않고 기존 걸 키우는 방향.
- **텍스트 파일(순수 JSON) 직접 파싱**은 지금 당장은 비권장 — 액터 레퍼런스
  (예: "어떤 아군 액터가 몇 번 매복 지점인지")를 JSON은 자연스럽게 못 담고
  문자열 경로로 우회해야 해서 손이 많이 감. 나중에 진짜 LLM/UDP 신호가 외부
  에서 JSON으로 들어오게 되면, 그건 "런타임에 수신하는 신호"고 지금 얘기하는
  "우리가 미리 짜두는 시나리오 단계표"랑은 다른 문제라 그때 가서 별도로
  붙이면 됨 — 지금 DataTable 선택과 충돌 안 함.

### 12-1. 매복 지점 기록 방식 — 확정

매복 지점은 시나리오 단계표(위 DataTable)랑 성격이 달라. 단계표는 "숫자/조건"
같은 추상적인 값이라 표로 편집해도 문제없는데, 매복 지점은 **"이 나무 뒤,
저 수풀 옆"처럼 눈으로 보면서 3D 뷰포트에서 잡아야 하는 값**이라, 표에 좌표
숫자를 직접 타이핑하는 건 위치 감각이 없어서 오히려 불편함. 그래서 둘을 같은
방식으로 통일하지 말고 **용도별로 다른 도구를 쓰는 걸 추천**:

- 레벨에 `AmbushMarker` 같은 단순 마커 액터(빈 액터 하나, 화살표 정도만
  보이는)를 매복 지점마다 하나씩 배치 — 뷰포트에서 드래그로 원하는 나무/
  수풀 뒤에 직접 가져다 놓으면 됨(눈으로 보고 배치하는 게 제일 정확함).
- 각 아군 BP 인스턴스는 "내 매복 지점" 프로퍼티로 이 마커 액터를 **참조**만
  가짐(레벨에서 드롭다운으로 지정, 또는 이름 규칙으로 자동 매칭 — 이
  프로젝트에서 이미 여러 컴포넌트가 쓰는 "이름으로 참조" 관례와 같은 결).
- 장점: 마커를 옮기면 아군도 자동으로 따라옴(좌표를 직접 들고 있는 게
  아니라 참조만 하므로), 나중에 레벨 지형이 바뀌어도 매커 위치만 다시
  잡으면 됨, 30명 전원의 좌표를 표에 일일이 타이핑할 필요 없음.
- 반대로 "시나리오 데이터 파일/DataTable에 좌표로 기록"하는 방식은, 나중에
  **레벨이 아예 여러 개**가 되거나(다른 지형에서도 같은 시나리오 재사용) 매복
  지점을 코드/외부 도구로 대량 생성/수정해야 할 일이 생기면 그때 유리함 —
  지금 단계(레벨 하나, 30개 정도, 눈으로 배치)에서는 마커 액터 방식이 더
  간단하고 실수도 적을 것 같음.

**확정: 마커 액터 + 참조 방식.** 나중에 정말 필요해지면(레벨이 여러 개가
되는 등) 데이터 파일 방식으로 바꿔도 아군 BP 쪽 코드는 "매복 지점이 어디냐"를
물어보는 인터페이스만 유지하면 되니 큰 재작업은 아님.
