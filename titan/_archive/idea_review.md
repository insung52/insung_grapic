# idea.md 리뷰 — 설계서(system_architecture_design_spec.md) 대조 결과

`idea.md`에서 제기한 질문들을 `260420_UGV에뮬레이터_상세설계_v1.pdf` 데이터화 결과
(`system_architecture_design_spec.md`)와 대조해서 답을 찾을 수 있는 것과, 여전히 확인이
필요한 것을 구분했다.

---

## 1. "원격통제장치? 그냥 에뮬레이터에 포함시키면 되는건가?"

**포함시키면 안 됨 — 설계서에서 이미 별개 개체로 명시돼 있음.** p.11 프로토콜 시퀀스
다이어그램에 정확히 이 둘이 별도 액터로 등장한다:

```
RemoteControl (원격통제장치)  ←UDP(8000/8001)→  UGV에뮬레이터
```

- **에뮬레이터**: 물리/렌더링 엔진. UGV_Period_BasicInfo, UGV_Period_ObjectDetectionResult
  같은 텔레메트리·탐지결과를 "주기적으로 쏴주는" 쪽. p.16/p.17 DFD에서 봐도 센서모의SW/
  환경모의SW/차량모의SW를 들고 있는 PC가 이거다.
- **원격통제장치(RemoteControl)**: 조이스틱 입력을 받아 RC_RemoteDriving/RC_Movement 같은
  제어 커맨드를 "보내고", 에뮬레이터가 보내주는 영상(RTSP)·텔레메트리를 화면에 그려주는
  쪽. p.7~10에 UI 설계까지 따로 있음(주행영상 전시, 상태정보 전시, 식별객체 bounding box
  전시 등).

즉 비유하면 **에뮬레이터 = 서버(권위 있는 시뮬레이션 상태를 들고 있는 쪽), 원격통제장치 =
클라이언트(조종석 UI, thin client)** 에 가깝다. Blender/Blender-MCP 비유보다는 드론
GCS(Ground Control Station) 패턴이 더 정확한 비유 — 에뮬레이터가 "비행체(시뮬레이션)",
원격통제장치가 "조종기+지상국 화면".

다만 p.14 서버랙 SW탑재도에서는 "원격통제장치" 박스가 오히려 "MUM-T SW(자체방호)"/
"MUM-T SW(UGV)" 를 물고 있고, "무인차량에뮬레이터"/"자기방호에뮬레이터" 박스는 그 자체로
끝(연결된 SW 라벨 없음) — p.6/p.11의 관계와 **라벨링이 서로 안 맞는다.** 원본 문서 자체의
불일치이니 LIG 쪽에 "MUM-T SW(UGV)가 에뮬레이터 PC에서 도는 거냐, 원격통제장치에서 도는
거냐" 로 콕 집어 물어볼 필요 있음.

**결론**: 최소 2개 프로세스(에뮬레이터 PC 1대 + 원격통제장치 PC 1대, 축당)로 나뉘는 게
설계 의도. 지금처럼 한 PC/한 프로세스에 렌더링+조종 UI를 합치는 건 시연용 단순화로는
가능하지만, "네트워크로 분리된 두 컴퓨터"라는 설계 의도 자체를 없애는 선택이라는 걸 인지하고
가야 함.

## 2. "서버랙 등 인프라까지 구현해야하나?"

**아니오, 이건 순수 물리 인프라(랙/스위치)라 소프트웨어 구현 대상이 아님.** p.14 다이어그램의
서버랙/KVM스위치/이더넷스위치 박스는 SW 라벨이 안 붙어 있는 순수 하드웨어 배치도 항목. 팀에서
신경 쓸 건 "저기에 들어가는 서버 4대(운용/GPU/빅데이터/가시화)가 뭘 하는 SW를 도는지"이지,
랙 자체를 구현하는 게 아님. 이건 확실히 넘겨도 되는 항목.

## 3. "GPU 서버 따로 있어야 할까? 모비젠쪽에서 전달받은거도 없고, 이미 targetdetection 구현해놓음"

**당신 판단이 맞을 가능성이 높음 — 근거도 있음.** p.14~15에서 GPU서버는:
- 스펙이 **Quadro PRO5000 48GB** (렌더링용 게이밍 GPU가 아니라 추론/워크스테이션급 카드) —
  에뮬레이터 PC들의 RTX 5070Ti(p.6, 순수 렌더링용)와 성격이 다름.
- 도는 SW는 **상황인식 모델 / 타격스케줄링 모델 / Object-To-Ontology 모델** — 이름부터
  지휘통제(C2) 쪽 AI 추론 서비스이지, 우리 쪽 렌더링/탐지 파이프라인이 아님.
- p.11 프로토콜에도 이 GPU서버 관련 ICD가 아예 등장하지 않음 (등장하는 액터는 RemoteControl/
  UGV에뮬레이터/ADU/RCWS 뿐).

즉 **GPU서버는 렌더링팀(우리) 책임이 아니라 모비젠이 만드는 지능형지휘통제 SW 스택의
일부**로 보는 게 설계서와 일치한다. 우리가 할 일은 이미 구현한 카메라 투영 기반
target detection 결과를 p.16/17 DFD의 "Raw DB/Fabric" 경로로 흘려보내 주는 인터페이스만
맞추면 되고, GPU서버 자체를 우리가 구현할 필요는 없어 보임. **다만 "없어도 된다"를 확정하려면
모비젠 ICD를 받아봐야 한다**는 원래 메모가 맞다 — 지금은 "우리 책임 아닌 것 같다" 정도까지만
확인됨.

## 4. "가시화 서버는 또 뭐지?"

p.14: 가시화서버 → **전투통합지휘 SW**. p.3의 "AIMD 상황도" 스크린샷(위협도 게이지, 부대
자산 리스트, 지도 위 적/아군 마커, 타임라인 스케줄링)이 아마 이 가시화서버가 그리는 화면.
즉 이것도 지능형 통합 지휘통제체계실 쪽 C2 소프트웨어(LIG 자체 제품 "AIMD" 계열)로 보이고,
**Unreal 에뮬레이터/원격통제장치와는 다른 팀의 산출물**일 가능성이 높다. 우리 쪽에서 신경
쓸 건 "이 서버가 우리 시뮬레이터로부터 어떤 데이터(위치/탐지결과/영상?)를 받아가야 하는지"
뿐 — 화면 자체를 우리가 만드는 게 아님.

**3~4번 종합**: 서버랙 4종 중 우리가 구현하는 건 사실상 없고, 우리는 **"Raw DB/Fabric"이라는
하나의 데이터 인터페이스에 우리 시뮬레이션 데이터(위치/탐지결과/영상)를 흘려보내는 발행자
(publisher)"** 역할만 하면 되는 그림. 이게 맞다면 범위가 크게 줄어든다 — 확정은 모비젠 ICD
수신 후.

## 5. 렌더링 부하 — "12번 렌더링" 문제, 설계서가 이미 답을 주고 있을 수도 있음

idea.md에서 걱정한 "한 서버에 12개 뷰(환경1+CCTV4+RCWS1 x2축 + UAV1) 몰아넣으면 부족하지
않을까" 문제 — **설계서 자체가 이미 1대가 아니라 2대로 나눠놨다**는 걸 p.6에서 확인했다:

- **UGV 에뮬레이터 구동 PC** (RTX 5070Ti 전용): UGV CCTV 4 + UGV RCWS뷰어 1 = 5뷰
- **자체방호 에뮬레이터 구동 PC** (RTX 5070Ti 전용, UAV 조이스틱도 여기 연결):
  주변환경카메라 1 + 트럭 CCTV 4 + 트럭 RCWS뷰어 1 + UAV카메라 1 = 7뷰

즉 "GPU서버 1대에 12개 다 몰아서 멀티플레이 동기화" 방향보다, **설계서가 원래 의도한 대로
2대의 독립 PC로 쪼개는 게 이미 정답에 가깝다.** 두 PC가 각각 5~7뷰만 감당하면 지금
"3번 렌더링 = 30fps(RTX5060)" 대비 부하 증가폭이 훨씬 완만하고, 스펙도 RTX 5070Ti로
업그레이드되니 여유가 더 생김.

남는 문제는 "완전한 UE 멀티플레이 리플리케이션"이 아니라 **가벼운 상태 동기화**로 보인다:
- UGV PC는 UGV의 위치/애니메이션을, 자체방호 PC는 트럭/UAV/RCWS 상태를 각자 권위 있게
  갖고 있고,
- 상대방 화면(트럭 CCTV에 UGV가 지나가는 모습, UGV 카메라에 UAV가 보이는 모습 등)에는
  **받은 transform을 그대로 보간해서 그리는 "고스트" 액터**만 있으면 됨.
- 이건 언리얼 기본 리플리케이션(권위/예측/롤백 다 갖춘 무거운 시스템)이 아니라 **NATS
  pub-sub로 transform/상태값만 주기적으로 던지고 받는 쪽에서 단순 보간**하는 정도로 충분할
  가능성이 큼 — 팀장님이 제안한 NATS 방향과 정확히 맞아떨어진다. 전체 소스 리플리케이션
  설정을 다 갈아엎을 필요 없이, "일부 액터를 네트워크로 받은 값으로 움직이는 더미 액터로
  만드는" 국지적 작업이면 될 수 있음.
- p.11 프로토콜의 10Hz/20Hz 주기 전송 패턴도 참고할 만함 — 텔레메트리는 10Hz, 조종 관련은
  20Hz로 이미 설계서가 권장 빈도를 제시하고 있어서, NATS 메시지 빈도 설계할 때 그대로
  참고 가능.

**주의**: UAV는 자체방호(트럭) PC의 조이스틱으로 조종하는데(p.6), UAV가 UGV 쪽 화면에도
보여야 한다면(현재 titan_example처럼 UAV가 자유롭게 날아다니는 구조라면) UAV 상태도 양쪽에
동기화 대상이 됨 — "누가 UAV의 권위(authority)를 갖는가"를 설계서 기준으로는 자체방호
PC 쪽으로 잡는 게 자연스러움.

## 6. RTSP 스트리밍 GPU→CPU 오버헤드

일반론으로 답할 수 있는 부분: 렌더타겟을 CPU로 readback해서 인코딩하면 그 자체가 병목이 되므로,
**NVENC 하드웨어 인코더가 GPU 메모리 상의 렌더타겟을 직접 읽어 인코딩하는 zero-copy 경로**를
쓰는 게 핵심. 언리얼 기본 Pixel Streaming 플러그인이 내부적으로 이 경로(NVENC 직결)를 쓰고
있지만 프로토콜이 WebRTC라 p.11이 요구하는 "RTSP(5)" 스펙과는 안 맞음 — RTSP로 내보내려면
① Pixel Streaming의 WebRTC 출력을 RTSP로 게이트웨이하는 중계 서버를 두거나 ② Media
Foundation/FFmpeg의 NVENC 하드웨어 경로를 직접 붙여 자체 RTSP 서버를 만드는 방법 중 하나를
검증해야 함. 이건 실제로 벤치마크해보기 전엔 이론으로만 말하기 어려운 영역이라 스파이크
작업으로 분리해두는 걸 추천.

## 7. Lumen + 씬캡쳐 FPS 버그

이미 알고 있는 이슈(`camera_pipeline_overhaul_2026-07.md`)와 idea.md의 결론이 일치함 —
"뷰 하나는 반드시 언리얼 기본 렌더링이어야 한다"는 제약이 이제 **2대의 PC 각각**에도
그대로 적용된다는 점만 짚어두면 됨: UGV PC에서는 UGV RCWS뷰어를, 자체방호 PC에서는
트럭 RCWS뷰어(또는 UAV뷰어)를 각각 그 PC의 "기본 렌더링 뷰"로 지정해야 두 PC 모두 버그를
피할 수 있음. PC가 2대로 늘어나면 이 제약을 "PC당 하나씩" 다시 챙겨야 한다는 뜻.

## 8. 종합 — 다음에 확인해야 할 것 (우선순위)

1. **원격통제장치 vs 무인차량/자기방호에뮬레이터의 SW 귀속 불일치** (p.6/p.11 vs p.14) —
   LIG에 직접 질문할 가치 있는 가장 명확한 모순점.
2. **모비젠 ICD 수신 대기 중** — GPU서버/가시화서버가 "우리 책임 아님"이라는 추정을 확정하려면
   필요. 받으면 "Raw DB/Fabric" 인터페이스 스펙(포맷/프로토콜, pub-sub이 정말 NATS 같은
   기술인지)도 같이 확인.
3. **UGV/자체방호를 물리적으로 2개 프로세스(PC)로 쪼갤지, 지금처럼 1개로 유지하되 시연만
   그렇게 보이게 할지** — 카덱스 시연 목적상 렌더링 부하 분산 효과도 있고 설계서 의도와도
   맞으니, 2 프로세스 분리 + NATS 경량 동기화 쪽이 현재로선 더 맞는 방향으로 보임(최종 판단은
   일정/인력 상황에 달림).
4. RTSP zero-copy 인코딩 경로는 별도 스파이크로 검증.
