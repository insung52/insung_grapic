원본: `documents/260806_시스템 구성도.pdf`(이미지 다이어그램 1장) + `documents/문의내용0806.md`

## 0. 시스템 구성도 원문 (재구성)

```
                              [상위체계] (LIG SW)
                             /                        \
              RTSP: CCTV영상,RCWS영상              (위로 화살표, 프로토콜 라벨 없음)
                    /                                    \
      [자체방호 통제기 SW]                          [원격 통제기]  ← LIG SW (회색! 우리가 안 만듦)
      (개발대상 SW)                                        |↕
             ↑USB: UAV,RCWS 제어                    UDP: 차량상태/RCWS인식결과/주행정보 (↑)
             |                                       UDP: 차량제어/RCWS제어 (↓)
       [조이스틱] (HW)                               RTSP: RCWS카메라영상/UGV주행영상 (↑)
                                                            |↕
                                                [UGV 시뮬레이션 SW] ← 개발대상 SW (우리)
                                                            ↑USB: UAV,RCWS 제어(원문 그대로,
      [조이스틱](HW, 원격통제기 쪽) ──USB──────────────────→ 아마 라벨 복붙 오류로 추정)
```

범례: 파란 테두리=개발대상 SW(우리), 회색=LIG SW, 연회색=HW.

## 1. 구조적 차이 — 심각도 순

### ① 자체방호(이동형지휘소) 축은 애초에 "에뮬레이터+콘솔 분리"가 아니라 **단일 프로그램**

Q&A 원문: *"이동형 지휘소 SW : UAV 제어 및 자체방호 RCWS 모사"* — 시뮬레이션과 제어가 한
SW에 묶여 있음. 다이어그램에도 "자체방호 통제기 SW" 박스 하나뿐, 별도 에뮬레이터 박스 없음
— 조이스틱이 이 박스에 USB로 바로 꽂히고, RTSP로 상위체계에 바로 송출.

**우리 계획**: §2(Layer B)에서 "자체방호축도 UGV처럼 네트워크 분리(에뮬레이터+원격통제장치
2프로세스)로 통일"하기로 결정했었음(`architecture_decisions.md` §2).

**→ 정면으로 배치됨.** 이 결정을 되돌려야 할 가능성이 높습니다 — 자체방호축은 원래
합쳐진 한 프로그램이 맞는 것으로 보임(계획 변경 시 "합치는 게 쉽다"던 원래 원칙과도 결이
맞음 — 오히려 잘 됐다고 볼 수도 있음).

### ② UGV 원격통제기는 **LIG가 만듦** — 우리 개발 대상이 아님, 소문이 아니라 확정 사실

다이어그램 범례상 "원격 통제기" 박스가 **회색(LIG SW)**. "우리가 만든 걸 보여주고 타사가
인계받을 수도 있다"던 이야기가, 알고보니 "타사"가 아니라 **LIG 자체**였고 이미 확정된
상태입니다.

**우리 계획**: `architecture_decisions.md` §1.4/§1.5에서 "UGV 통제기SW도 우리가 만들기로
확정, 플러그인 계층화까지 설계"했음.

**→ 이 작업 범위가 통째로 필요 없어질 가능성.** 다만 우리 자체 테스트/검증용 레퍼런스
클라이언트로는 여전히 가치 있을 수 있음(연동 테스트 시 LIG 원격통제기가 준비 안 됐을 때
대역할).

### ③ UGV축과 자체방호축을 잇는 연결이 다이어그램에 전혀 없음 — **가장 중요한 미해결 질문**

이 다이어그램엔 "UGV 시뮬레이션 SW"와 "자체방호 통제기 SW"를 잇는 선이 **하나도 없습니다.**
둘 다 각자 독립적으로 상위체계와만 통신하는 구조로 그려져 있음.

**우리 계획 전체(Layer C, 리플리케이션)**: UGV PC와 자체방호 PC가 언리얼 네이티브
리플리케이션으로 "하나의 배틀필드"를 공유해야 한다는 전제 위에 리슨서버/45명 캐릭터
리플리케이션/RCWS 히트스캔+Multicast 설계를 전부 세웠고, 오늘 트랙4가 그 감사(코드 조사)까지
끝냄(`replication_audit.md`).

이 전제는 원본 PDF(p.18 시나리오)의 *"자체방호플랫폼과 UGV는 같은 가상환경을 공유가능하게
(RPG처럼)"*에서 나온 겁니다. **이번 시스템 구성도가 그 요구사항을 철회한 건지, 아니면
그냥 이 레벨의 다이어그램(SW 간 통신 프로토콜 정의용)엔 원래 안 그리는 링크인 건지 구분이
안 됩니다.** 만약 정말로 UGV/자체방호가 서로 안 이어져 있다면(각자 독립된 시뮬레이션이고
같은 가상환경을 공유하지 않는다면), **오늘 트랙4가 끝낸 리플리케이션 감사·설계 작업
전체가 필요 없어집니다** — 반대로 여전히 공유해야 한다면 이 다이어그램에 단순히 누락된
것뿐이고 우리 작업은 그대로 유효합니다. **LIG에 바로 확인이 필요한 1순위 질문.**

## 2. 전송 계층 차이

### UGV축(원격통제기 ↔ UGV 시뮬레이션 SW): UDP + JSON, NATS 아님 — 확정 사실, 선택지 아님

Q&A: *"UGV의 제어나 상태정보의 송수신 통신프로토콜은 UDP 기반 JSON String으로 이루어집니다."*
IP/포트까지 확정 제공됨:

| 단말 | IP | Port(주기) | Port(비주기) |
|---|---|---|---|
| UGV | 192.168.10.10 | 8000 | 8001 |
| 원격통제기 | 192.168.10.20 | 8010 | 8011 |

메시지 구조(원문 그대로):
```json
{
  "cmd": "Command Code",
  "src": "device",
  "recv": "device",
  "data": { "key1": "value1", "key2": "value2" }
}
```
device 코드: `RC=20`, `UGV=14`, `UGV_RCWS=13`, `UGV_ADU=12`

신뢰성은 NATS/JetStream이 아니라 **애플리케이션 레벨 ACK+재시도**로 처리(`image.png`):
- 주기성 메시지(Request/Response): 응답 없으면 N회까지 Request 재시도
- 이벤트 메시지(Message/ACK): `( )msec` 내 ACK 없으면 3회까지 재시도

**우리 계획**: `protocol_icd.md` §0에서 "v1 전부 NATS(TCP), UDP 도입 안 함"으로 명시적으로
결정하고, "PoC에서 문제되면 그때 UDP로 분리"라고 후순위로 미뤄뒀었음.

**→ 정반대로 확정됨.** 이건 우리가 선택할 수 있는 문제가 아니라 **원격통제기가 LIG 소프트웨어라
그쪽이 구현한 대로 우리가 맞춰야 하는 외부 제약**입니다. `protocol_icd.md`의 봉투 포맷
(`{cmd,seq,ts,payload}`)도 LIG 포맷(`{cmd,src,recv,data}`)으로 다시 맞춰야 함. 다행히
원래 원본 PDF(p.11)가 이미 UDP+포트 기반이었어서, 방향 자체는 "우리가 NATS로 갔다가 다시
원점으로 돌아오는" 셈 — p.11 분석해뒀던 내용을 상당 부분 재사용 가능.

**참고**: 자체방호축은 위 ①에 따라 원격통제기 자체가 없어서, 이 UDP/JSON 프로토콜이 자체방호축에도
적용되는지는 불명확(다이어그램상 자체방호통제기SW의 외부 통신은 USB 조이스틱 + RTSP 업로드뿐,
JSON 커맨드 채널이 안 보임).

## 3. Layer A(상위체계 연동) — 사실상 미정, 우리가 앞서 짠 설계는 "확정된 미래"가 아니라 "선제 초안"

Q&A 원문: *"금일 확인 한 내용으로는 아직 자체방호통제기에서 상위 체계로 가는 ICD 정의는
안되어있고, 향후 추가 여부도 LIG 검토중에 있습니다."*

즉 상위체계가 자체방호축에 명령을 하달하는 채널 자체가 **아직 있을지 없을지도 안 정해짐.**
다이어그램에도 자체방호통제기SW→상위체계는 RTSP(영상)만 있고 반대 방향(명령 하달) 화살표가
없음. UGV축도 원격통제기→상위체계 화살표에 프로토콜 라벨이 없어서(다른 링크는 다 라벨이
있는데 이것만 없음) 미정으로 보임.

**우리 계획**: `protocol_icd.md` §5(HQ_/RPT_ 메시지 전체), `architecture_decisions.md` §3
(시나리오 #4-1~4-8 메시지 체인, 교전승인 게이트)을 상당히 구체적으로 설계했고, 오늘 트랙3이
파이썬 스텁까지 완성함(`hq_stub/`).

**→ 이 작업들이 "틀린" 건 아니지만, "확정된 스펙 구현"이 아니라 "LIG가 나중에 이 채널을
추가하기로 하면 바로 쓸 수 있는 선제 설계"로 위상이 낮아짐.** 폐기할 필요는 없음(LIG가
검토 중이라고 했지 안 한다고는 안 했음) — 다만 우선순위/일정에서 "확정 스펙 구현" 트랙들
(UGV축 UDP/JSON)보다 뒤로 밀려야 할 것 같음.

## 4. 일치하는 것 (변경 불필요)

- **하드웨어 스펙**: Ryzen 9800X3D / RAM 16GB / RTX 5070Ti — 원본 PDF(p.6)와 정확히 일치,
  "LIG에 납품한 장비"라 실물 확정.
- **RCWS/ADU 서브시스템 분리 개념**: device 코드에 `UGV`/`UGV_RCWS`/`UGV_ADU`가 따로 있는 것도
  원본 PDF p.11의 `/UGV`, `/ADU`, `/RCWS` 태그 구분과 일치.
- **영상은 RTSP**: 우리 판단(NVENC+GStreamer 자체구현) 그대로 유효 — RTSP라는 프로토콜
  선택 자체는 안 바뀜, 트랙1(PoC) 계속 진행하면 됨.
- **UI는 "B안 + 톤앤매너"로 진행하라는 지시** — 이건 우리 대화에 없던 사전 논의(사용자가 이미
  LIG와 별도로 주고받은 내용)라 제가 아는 바 없음. 참고할 자료 있으면 공유 부탁드립니다.

## 5. 우선순위 재정리 제안

1. **[LIG 재확인 최우선] UGV축과 자체방호축이 정말 서로 안 이어지는지** — 답에 따라
   트랙4(리플리케이션) 작업 전체의 존폐가 갈림.
2. UGV축 프로토콜을 LIG의 UDP+JSON(`{cmd,src,recv,data}`, 실제 IP/포트) 스펙으로
   `protocol_icd.md` 재작성.
3. 자체방호축 설계를 "단일 프로그램(에뮬레이터+조이스틱 제어 통합)"으로 되돌리기 —
   `architecture_decisions.md` §1.5(플러그인 계층화)/§2 대폭 수정.
4. UGV축 통제기SW(Track 6/7) 작업 범위를 "우리 자체 테스트용 레퍼런스"로 축소.
5. Layer A(HQ_/RPT_) 관련 트랙은 계속 준비하되 우선순위를 낮춤 — LIG 확정 소식 나오면 즉시
   재우선순위화.
