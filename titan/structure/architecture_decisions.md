## 0. 한눈에 보기

- **총 5개 SW**: UGV 에뮬레이터, UGV 통제기SW, 자체방호 에뮬레이터, 자체방호 통제기SW,
  상위체계(우리가 구현 안 함 — 테스트용 파이썬 스텁으로 대체, 실물은 모비젠/LIG 영역).
  **UGV 통제기SW는 타사가 만들 가능성이 있다고 들었으나, 우리도 만들기로 확정** — "우리가
  만든 걸 보여주고 타사가 수정/인계받는" 흐름 가능성 있어 §2 프로토콜을 타사가 그대로 갖다
  구현해도 되는 ICD 수준으로 격상함(`protocol_icd.md`).
- **3계층 프로토콜**: (A) 상위체계↔통제기SW, (B) 통제기SW↔에뮬레이터, (C) 에뮬레이터↔에뮬레이터.
  **(A)(B) 둘 다 v1은 NATS(TCP)로 통일**, RTSP만 별도. UDP는 도입 안 함(§2 참고, 필요시 후순위 분리).
- **코드베이스는 2벌만**: 에뮬레이터(UGV/자체방호 공용, 런타임에 모드 선택) + 통제기SW
  (공통 플러그인 + 축별 얇은 프로젝트, §1.4). "SW 5개"는 코드베이스가 아니라 **런타임에 뜨는
  프로세스 개수**를 세는 것.
- 지휘통제플랫폼 서버랙(운용/GPU/빅데이터/가시화서버)은 우리 책임 아닌 것으로 추정,
  Raw DB/Fabric에 텔레메트리 발행하는 인터페이스(NATS)만 맞추면 될 가능성 높음 — **모비젠
  ICD 수신 전까지 가정 단계**.

```
                              상위체계 (판단권한 — 모비젠/LIG 실물, 지금은 파이썬 스텁)
                             /                                    \
                  (A) NATS: HQ_*(하달) / RPT_*(보고)
                           /                                        \
                자체방호 통제기SW                                UGV 통제기SW  ← 타사 인계 가능성
                     |  (B) NATS+RTSP: RC_*(명령) / TRK_*(텔레메트리) / 영상   |
                     ↓                                              ↓
              자체방호 에뮬레이터 ⟷⟷⟷ (C) 언리얼 리플리케이션 ⟷⟷⟷ UGV 에뮬레이터
                  (둘 다 titan_example, 런타임에 축/호스트-클라이언트 선택)
```

## 1. Layer C — 에뮬레이터 ↔ 에뮬레이터 (언리얼 네이티브 리플리케이션)

### 1.1 코드베이스: `titan_example` 하나, 런타임 모드 선택

UGV/자체방호 두 프로세스는 **같은 프로젝트/실행파일**에서 나옴 — RCWSComponent, 차량 물리,
리플리케이션 세팅 등 공유 코드를 두 곳에서 따로 관리하지 않기 위함. 패키징 시 또는 실행 시
"차량모드(UGV/자체방호)"를 선택. (이건 "프로세스는 분리, 코드는 공유"라 §4-1 분리 우선
원칙과 안 부딪힘 — 그 원칙은 네트워크/프로세스 경계 얘기지 소스코드 얘기가 아니었음.)

### 1.2 토폴로지: 리슨서버, UGV PC가 기본 호스트, 런타임 선택 가능

- **전용서버(Dedicated Server) 방식은 폐기.** 에뮬레이터라는 개념 자체가 "현실을 대체"하는
  것이라, 실제로는 둘을 중계하는 제3의 서버가 존재할 자리가 없음 + 서버랙에 여유 자원이
  진짜 있을지도 불확실(하드웨어 스펙을 계속 못 받는 상황) — 존재 여부가 불확실한 하드웨어에
  의존하는 설계는 피함(§4-5).
- **리슨서버**: 자체방호 PC가 7개 씬(환경1+CCTV4+RCWS1+UAV1), UGV PC가 5개 씬(CCTV4+RCWS1)을
  렌더링 — 이미 부하가 더 적은 **UGV PC를 기본 호스트**로 함(여유 있는 쪽에 서버 부하를 얹는
  게 합리적).
- **호스트/클라이언트도 런타임 선택 가능하게**: "차량모드"와 같은 패턴으로 시작 시점에
  호스트/클라이언트 역할도 고를 수 있게 구현(언리얼의 `?Listen`/`<IP>` 맵 URL 메커니즘으로
  낮은 비용에 가능). 부수 효과: 리슨서버는 클라이언트가 안 붙어도 싱글플레이처럼 동작해서
  한쪽 PC만 켜고 솔로 개발/테스트도 자연스럽게 됨.

### 1.3 리플리케이션 대상

- 아군/적군 45명 캐릭터(이동/애니메이션/체력/사망 — 표준 `CharacterMovementComponent`
  리플리케이션으로 대부분 커버, 커스텀 상태만 `Replicated`+`OnRep` 추가), UGV/트럭 차량
  상태(Chaos Vehicle 네트워크 프리딕션, UE5.1+ 기본 지원 확인 필요).
- **RCWS 발사**: 액터 리플리케이션 안 함. **히트스캔 + Multicast RPC** — 서버가 판정, 결과만
  멀티캐스트로 뿌려서 각 클라이언트가 로컬로 트레이서/이펙트 스폰.
- **아군 30명은 UGV에 종속된 로컬 팔로워 개념** — 별도 통신 없이 UGV 에뮬레이터 내부 AI
  로직으로 처리. 리플리케이션 대상이지만 Layer A/B 프로토콜엔 안 나타남.
- **감사 필요 코드** (착수는 설계 완전히 끝난 뒤로 미룸): `RCWSComponent`/
  `RCWSFireControlComponent`, `UGVMovementComponent`/`UGVAIController`,
  `titan_examplePlayerController`, 아군/시나리오 스폰 시스템.

### 1.4 통제기SW 구조: 플러그인 계층화 (2번째 코드베이스)

에뮬레이터와 달리 "공통 플러그인 + 축별 얇은 프로젝트"로 추천:
- **공통 플러그인**: RTSP 수신(MediaTexture), NATS 프로토콜 클라이언트, 공용 WBP 베이스
  위젯(게이지/영상패널 등)
- **축별 프로젝트/모듈**: 조이스틱 하드웨어 바인딩(UGV=TRUSTMASTER T-1600M FCS, 자체방호=
  제닉스 타이탄 GP5 — 실제 다를 수 있음), 축별 UI 레이아웃

에뮬레이터(단일 프로젝트+런타임 전환)보다 여기서 플러그인 분리를 더 미는 이유: (1) 조이스틱
하드웨어 차이가 실제로 있음, (2) **UGV 통제기SW가 타사로 갈 경우, 공통 플러그인만 있으면
우리 자체 테스트/레퍼런스용 UGV 콘솔도 거의 공짜로 만들 수 있어서 나중에 그쪽과 연동 테스트할
때 유리함**.

## 2. Layer B — 통제기SW ↔ 에뮬레이터

**상세 스펙은 `protocol_icd.md` §3~4.** 요약:
- 원격통제장치는 에뮬레이터의 리플리케이션 세션에 참여하지 않는 별도 프로토콜 클라이언트.
- 콘솔은 UGV축/자체방호축 둘 다 **네트워크 분리(NATS) 구조로 통일** — 원 설계서(p.16)의
  HDMI/USB 로컬 직결안은 폐기. 조이스틱은 콘솔(원격통제장치) PC에 물림(p.6 하드웨어표와
  다른 점, 의도적 결정).
- **전송은 v1 전부 NATS** (RTSP 제외) — 연결/BIT 핸드셰이크, 조이스틱 연속입력, 텔레메트리,
  단발성 명령/이벤트 전부. 원 설계서(p.11)는 UDP였지만, PoC에서 TCP head-of-line blocking으로
  체감 끊김이 확인될 때만 그 메시지들을 UDP로 분리(비용이 작은 변경이라 후순위로 미룸).
- **RTSP 영상**: UGV축 5스트림(CCTV 4 + RCWS뷰어), 자체방호축 7스트림(환경카메라+CCTV4+
  RCWS뷰어+UAV드론뷰). **인코딩은 UE 자체 NVENC(zero-copy) + `gst-rtsp-server`(GStreamer,
  인코딩된 비트스트림만 전달) 하이브리드로 결정** — 유료 OWL 플러그인 대체(§6 참고, PoC
  1~2일/안정화 1~2주 예상).
- 명령은 가능한 한 이미 구현된 함수/enum에 매핑(`SetUGVMode`/`EUGVDriveMode`,
  `SetRCWSMode`/`ERCWSControlMode`) — API 설계와 구현 비용을 같이 낮춤.
- 이 데모 시나리오 한정으로는 `RC_ManualDrive`/`RC_MissionWaypoint`는 거의 안 쓰임(UGV는
  항상 Auto 자동주행) — 자유주행/테스트 모드를 위해 프로토콜엔 남겨둠.
- 자체방호(트럭) 자체 조향/주행 기능 없음(확정) — 이 축 프로토콜엔 드라이브 커맨드 없음.

## 3. Layer A — 상위체계 ↔ 통제기SW

**상세 스펙은 `protocol_icd.md` §5.** NATS(TCP) pub-sub, JetStream 사용(연결 끊겨도 메시지
유실 안 되게 — 재연결 시 놓친 것부터 재생). Subject: `hq.cmd.selfdefense`/`hq.cmd.ugv`(하달),
`hq.rpt.selfdefense`/`hq.rpt.ugv`(보고). 상위체계가 양쪽 다 구독/발행하는 허브-스포크.

### 판단/보고 게이트 원칙

> **위험하거나 비가역적인 행동(발사/교전)에만 승인 게이트를 넣는다.** 저위험/가역적
> 행동(정찰, 이동, 카메라·짐벌 조작)에는 안 넣음. 승인과 별개로 상위체계가 상황을 계속
> 인지해야 하는 지점엔 승인 없는 FYI 보고를 추가할 수 있음 — "판단"과 "보고"는 다른 카테고리.

**교전승인 게이트**: 모드 전환이 아니라 발사 자체의 게이트. `RCWSFireControlComponent`에
`bEngagementAuthorized`(기본값 off/토글 가능) — Remote 수동격발/AutoFire 자동사격 둘 다 이
플래그를 체크. 승인 안 나도 AutoSurveillance/AutoAim(조준·추적)까지는 자유, 방아쇠만 잠김.
**상위체계 연동 전까지는 이 게이트를 꺼둔 채로 나머지 기능을 테스트.**

### 시나리오 단계별 메시지 체인 요약 (전체는 `protocol_icd.md` §5)

#4-1(침투보고) → #4-2(정찰) → #4-3(식별, FYI보고) → #4-4(이동명령) → #4-5(도착, FYI보고) →
#4-6(포착→교전승인 요청) → #4-7(교전개시 FYI+결과보고) → #4-8(잔적 교전승인→최종섬멸→
`RPT_ScenarioComplete`).

폐기됨: UGV 주행모드의 `STAY`/`EMERGENCY`(원문 p.11엔 있었으나 `Idle`이 이미 커버, 실질
기능 차이 없어 제거). 아군 개별 통신, "기어변경 승인" 등 지나치게 기계적인 단계는 의도적으로
안 넣음.

## 4. 재사용 가능한 설계 원칙 모음

1. **분리 우선(구조적 경계에 한함)**: 나중에 합치는 게 나중에 분리하는 것보다 항상 쌈 —
   프로세스/네트워크 경계처럼 되돌리기 비싼 결정은 분리를 기본값으로.
2. **자동 vs 게이트**: 위험/비가역 행동에만 승인 게이트, 나머지는 즉시 실행 + FYI 보고.
3. **트리거 소스와 이벤트 처리 로직 분리**: 실물 연동 전엔 콘솔 명령/디버그 버튼으로 스텁,
   나중에 신호 소스만 교체(`UScenarioStateSubsystem::BeginEnemyContactScenario()` 패턴).
4. **기존 함수/enum에 올라타기**: 새 프로토콜 명령은 가능하면 이미 구현된 함수 시그니처에
   매핑 — API 설계와 구현 비용을 같이 낮춤.
5. **되돌리기 싼 결정은 나중으로 미룬다**: 전송 방식(UDP vs NATS)처럼 메시지 스키마/통신
   상대를 안 바꾸는 결정은 지금 단순한 쪽(NATS 통일)으로 시작하고, 실측이 필요를 증명하면
   그때 쪼갠다. 구조적 경계(1번)와는 반대로 "일단 단순하게, 필요할 때 분리"가 맞는 축도 있음.
6. **불확실한 하드웨어에 의존하지 않는다**: 스펙을 계속 못 받는 상황이라, "어딘가에 여유
   자원이 있을 것" 같은 가정 위에 설계하지 않음(전용서버 폐기 사례).

## 6. 남은 미확정/블로킹 항목

**우선순위 높음 (우리끼리 정할 수 있음)**:
- **UGV 통제기SW 타사 제작 여부 최종 확인** — 확정이든 아니든 우리가 만들긴 하지만, 확정되면
  ICD(`protocol_icd.md`)를 그쪽에 넘길 준비(문서 형태/언어 등) 필요.
- RTSP PoC (NVENC+GStreamer `gst-rtsp-server`, appsrc 경로 — 고정 텍스처 하나 스트리밍부터
  시작해서 배관 확인, 이후 5/7스트림 동시 성능 검증)
