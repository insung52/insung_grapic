## 0. 신뢰도 표기 — 읽는 법

이 대화 과정에서 "확인하지 않은 것을 세밀하게 쓴" 항목이 세 번 틀렸다(상하체 분리 / 워핑이
8방향을 줄여준다 / IK는 항상 마지막). 그래서 모든 항목에 신뢰도를 붙인다.

| 표기 | 뜻 |
|---|---|
| **[A] 확정** | 근거를 확인했다. 바뀌면 구조가 바뀐다 |
| **[B] 잠정** | 합리적이나 실측 전. 바뀔 수 있다 |
| **[C] 미측정** | 지금은 모른다. 측정 항목과 판정 기준만 적는다 |

**[C]가 줄어드는 것이 곧 진척도다.** 전체 [C] 목록은 10절.

## 1. 층 경계 — 애니메이션 층의 책임

설계 문서 4절의 5계층 중 **L4 MOTION**이 이 문서의 대상이다.

```
L0 COMMAND → L1 SQUAD → L2 BRAIN → L3 ACT → 【L4 MOTION】
```

| 애니메이션 층이 책임지는 것 | 책임지지 않는 것 |
|---|---|
| 의도를 몸으로 바꾸는 모든 것 | **무엇을 할지 고르는 것** (L2) |
| 수렴(연속 값이 목표로 가는 과정)과 그 시간 상수 | 목표값이 무엇이어야 하는지 |
| 자율 현상(호흡·미세 떨림·시선 스캔) | 그 현상의 변조 파라미터(피로·긴장) |
| 지형·접촉 대응(발 배치, 접점 정렬) | 어디로 갈지 |
| **최종 총구 트랜스폼 산출** | 명중 판정 (게임플레이) |

**규칙 [A]**: L4는 **`FSoldierPoseIntent`와 월드(지형/충돌)** 말고는 아무것도 읽지 않는다.
액터 변수를 직접 읽지 않는다.

> 근거: `titan_example`은 애님BP가 액터의 `AimPitch`/`IsKneeling`/`IsProne`/`IsDead`를 매 틱
> 직접 읽었고, 그 결과 사망 시 그 값들을 일일이 중립으로 리셋해야 사망 몽타주가 정상 재생됐다
> (`../../ai_combat/enemy_ai_combat_system_status.md` 4절). GASP는 반대로 `S_CharacterPropertiesForAnimation`
> 구조체 하나로만 통신한다(분석 문서 8절). **후자를 따른다.**

## 2. 분류 원칙 — 결정 / 수렴 / 자율 [A]

새 항목이 생겼을 때 **"AI냐 애니메이션이냐"를 감으로 정하지 않기 위한 판정 규칙**이다.

| 종류 | 정의 | 소속 | 예 |
|---|---|---|---|
| **결정** | 이산적 선택. **이유가 있고**, 다르게 선택할 수도 있었음 | AI (L2/L3) | 엎드릴까, 어느 엄폐물로, 쏠까, 재장전할까, 어느 무기 자세로 |
| **수렴** | 결정을 몸이 따라가는 연속 과정. **생체역학적 시간 상수**를 가짐 | 애니메이션 (L4) | 조준선이 표적으로 수렴, 자세 높이가 목표로 내려감, 몸통이 목표 방향으로 돎 |
| **자율** | **아무도 결정하지 않음.** 항상 돌아가고 다른 상태에 의해 변조만 됨 | 애니메이션 (L4) | 호흡, 미세 떨림, 무게중심 잔떨림, 유휴 시 무기 만지작거림 |

### 2.1 판정 예시 — 호흡

호흡은 명백히 **자율**이다. AI가 "숨을 쉬자"고 결정하지 않는다. 다만 주기와 세기는 다른 상태의
함수다.

```
BreathPhase(t)  ← L4가 자체 생성 (기본파 + 노이즈, 개체별 위상 offset)
    주기   ← f(이동 속도, 피로도, 부상, 긴장도)
    진폭   ← f(같은 것들)
    일시정지 ← "숨 참기"는 결정에 가깝다 → L3가 플래그로 요청

AI가 주는 것    : 피로도·긴장도·부상 (상태값)
AI가 안 주는 것 : 호흡 위상, 주기 숫자
```

**"AI는 지쳤다는 사실만 말하고, 호흡이 얼마나 가빠지는지는 애니메이션이 정한다."**

### 2.2 판정 예시 — 피격

피격은 **한 항목이 아니라 두 항목**이다. 이걸 안 나눠서 이전 프로젝트가 `IsDead` 하나로
처리하다 문제가 났다.

| 측면 | 종류 | 수명 | 소속 |
|---|---|---|---|
| **맞은 순간**(플린치, 임펄스) | 외부 이벤트 → 자율적 반응 | 0.2~1초 | L4 |
| **다친 상태**(부상) | 상태값 | 지속 | L2가 보유, L4가 변조 입력으로 사용 |

## 3. 계약 — `FSoldierPoseIntent` [A]

### 3.1 원칙: AI는 애니메이션 축을 직접 건드리지 않는다

축은 반드시 늘고, 쪼개지고, 합쳐진다(예: "자세 높이" 하나가 나중에 "골반 높이 + 상체 굽힘"으로
갈라짐). 그때마다 AI 코드를 고치지 않으려면 한 겹을 둬야 한다.

```
AI는 "의미"를 말한다        →  Resolver가 "축 값"으로 번역  →  L4가 소비한다
   Posture = Prone                StanceHeight = 0.08
   Stress  = 0.8                  BreathRate ×1.6, SwayAmp ×1.4
   Suppressed = true              FlinchGain 0.7, AimSettleTime ×2.1
```

**축이 갈라지면 Resolver 한 곳만 고친다. AI 코드는 안 바뀐다.**

### 3.2 구조

```cpp
USTRUCT()
struct FSoldierPoseIntent          // L3 → L4. 이것이 유일한 통로다
{
    FLocomotionIntent   Locomotion;   // 목표 속도/방향/gait/회랑
    FPostureIntent      Posture;      // 자세 앵커(이산) + 목표 높이/기울기(연속) + 긴급도
    FFacingIntent       Facing;       // 몸 방향 모드 + 목표
    FWeaponIntent       Weapon;       // 무기 자세, 조준 목표, 발사 허가
    FGazeIntent         Gaze;         // 시선 목표 (조준과 별개)
    FInteractionIntent  Interaction;  // SmartObject 슬롯, 접점 트랜스폼
    FModulation         Modulation;   // 부상/피로/긴장/피제압/하중 → 자율 발생기 변조
};
```

**새 항목은 이 7개 필드 중 하나에 들어간다. 필드를 새로 만드는 일은 거의 없어야 한다.**

### 3.3 GASP 계약과의 대응 [A]

GASP의 `S_CharacterPropertiesForAnimation`이 이미 같은 역할을 한다(분석 문서 8절). 우리 계약은
그것의 확장이다.

| GASP | 우리 | 비고 |
|---|---|---|
| `inputState`(wantsToSprint/Walk/Strafe/Aim/Crouch) | `Locomotion` + `Posture` + `Facing` | **플레이어 입력 구조체를 AI 출력 구조체로 바꾸는 것이 전부** |
| `orientationIntent` | `Facing.TargetRotation` | 몸 방향 |
| `aimingRotation` | `Weapon.AimTarget` | **GASP도 이미 몸방향과 조준을 분리해뒀다** |
| `stance` (Stand/Crouch 이산) | `Posture.Anchor` + `Posture.TargetHeight` | **연속으로 확장**(6.2) |
| `rotationMode` | `Facing.Mode` | |
| `gait` / `movementMode` / `movementDirection` | `Locomotion` | 그대로 |
| — | `Gaze` / `Modulation` | **신규** |

### 3.4 AI가 실제로 배선해야 하는 것 [A]

분석 문서 8.2절에서 확인된 통합 지점:

```
조준 방향  ← AIController의 컨트롤 로테이션 (SetFocus / SetControlRotation)
             → aimingRotation → Get_AOValue → 상체 조준
몸 방향    ← CMC의 bOrientRotationToMovement / bUseControllerDesiredRotation
회전 모드  ← 같은 CMC 플래그
자세/gait  ← inputState 자리에 AI 결정을 채움
궤적 회전  ← PreviousDesiredControllerYaw
```

**AIController의 컨트롤 로테이션 하나가 조준 체인 전체를 구동한다.**

## 5. 합성 파이프라인 [A]

### 5.1 IK는 두 종류다

**"IK는 항상 마지막"은 틀린 규칙이다.** IK에 절대 권한을 주면 총구는 항상 완벽히 정렬되고 발은
절대 안 미끄러지는 무균 상태가 된다.

| | **결합(Coupling) IK** | **목표(Goal) IK** |
|---|---|---|
| 하는 일 | 부위 간 **물리적 부착 유지** — 왼손이 총열을 잡음, 발이 지면에 닿음 | 몸을 표적 쪽으로 **정렬** |
| 성격 | 제약(constraint). 실제로 붙어 있다 | 목표(goal). **오차가 남는 게 정상** |
| 위치 | 뒤쪽 | **교란보다 앞** |
| 권한 | 높지만 **깨질 수 있음**(부상/피격 시 해제) | 이득(gain) < 1 |

### 5.2 순서

```
1  로코모션 베이스        MM이 선택한 풀바디 포즈
2  자세 변형              높이(연속) · 좌우 기울기                     [전신]
3  무기 자세 앵커         정조준/견착대기/허리/맹목/내림               [애디티브]
4  조준 오프셋            yaw/pitch                                    [애디티브]
   ───── 여기까지 "이동하는 몸" + "조준하려는 의도" ─────
5  안정화 IK (Goal, gain<1)  로코모션 흔들림을 부분적으로 상쇄
                             gain = 숙련도 × (1−부상) × (1−피로)
   ───── 여기서 "얼마나 총을 잡아주는가"가 결정 ─────
6  교란                   호흡 · 미세 떨림 · 반동 잔여 · 피제압 플린치
                          ↑ 상쇄되지 않는다. 총구가 실제로 흔들린다
7  결합 IK (권한 가변)    왼손↔총 그립 · 발↔지면
                          alpha ← 부상/피격/균형 상태가 낮추거나 끊음
8  물리                   피격 임펄스 · 부분 래그돌
   ───── 최종 총구 트랜스폼 = 게임플레이가 읽는 값 ─────
```

**5와 6의 순서가 핵심이다.** 조준 정렬이 교란보다 앞이므로 호흡·떨림이 총구에 그대로 남는다.
정밀 조준 시 흔들림이 줄어드는 것은 IK가 보정해서가 아니라 **6단계의 진폭이 줄어서**다.

### 5.3 GASP 그래프에 대응 [A]

분석 문서 2절의 실제 위상과 대조하면:

| 우리 단계 | GASP 위치 | 방식 |
|---|---|---|
| 1 | `MotionMatching_0 → BlendListByInt_0` | 그대로 승계 |
| 2 자세 변형 | IK 구간, `FootPlacement` **앞** | Control Rig 신규 |
| 3 무기 앵커 | 애디티브 구간, 조준 오프셋 **앞** | 애디티브 추가 |
| 4 조준 오프셋 | `BlendSpacePlayer_1`(`BS_Neutral_AO_Stand`) **교체/확장** | **자리가 이미 있다** |
| 5·6 | IK 구간 진입 직후 | **Control Rig 내부에서 순서 처리** |
| 7 | `FootPlacement`/`LegIK` 구간 + 손 그립 CR | 기존 + 추가 |
| 8 | 이후 별도 경로 | PhysicsControl (2차) |

### 5.4 제약 — 교란은 애디티브가 아니라 Control Rig 연산으로 [A]

GASP에서 **애디티브는 로컬/메시 공간, IK는 컴포넌트 공간**이다. 교란을 애디티브 블렌드스페이스로
만들면 IK보다 **앞**에 놓이게 되어 5.2의 순서가 뒤집힌다.

```
IK 구간
  LocalToComponentSpace
    → [CR-A: 조준 정렬(gain<1) → 호흡/떨림 교란 → 총구 최종 오프셋]
    → [CR-B: 자세 높이]
    → FootPlacement → LegIK
    → [CR-C: 왼손 그립 결합]
  ComponentToLocalSpace
```

Control Rig은 내부 실행 순서를 우리가 정하므로 공간 변환 비용 없이 규칙을 지킬 수 있다.

### 5.5 부산물 — 탄착 오차를 난수로 만들지 않는다 [B]

이 파이프라인이면 총구가 실제로 흔들리므로 오차가 물리적으로 존재한다.

```
탄착 = 실제 총구 트랜스폼에서 발사
오차의 출처 = 호흡 진폭 · 떨림 · 안정화 gain · 반동 잔여 · 이동 속도 · 부상
```

설계 문서 6.2절의 난수 콘(`BulletSpreadDegrees`)은 **무기 자체의 기계적 산포**(총열/탄약 편차)로
축소한다. "왜 빗나갔는가"가 상태로 설명되고 총구 궤적을 그려서 디버깅할 수 있다.

> **[B] 근거**: 원리적으로 타당하나, 실제로 흔들림 진폭이 게임플레이에 쓸 만한 크기의 오차를
> 만드는지는 튜닝해봐야 안다. 너무 작으면 여전히 완벽 명중, 너무 크면 통제 불능.

|---|---|
| **타입** | 연속 (속도 벡터) + 이산 (gait: Walk/Run/Sprint) |
| **분류** | 목표=결정(L2), 실제 속도=수렴(CMC 물리) |
| **생성** | **Motion Matching** — 데이터 주도 [A] |
| **앵커** | GASP 1,450 클립 (Walk 452 / Run 457 / Crouch 431 / Sprint 65 / Idle 48) **확보됨** |
| **파이프라인** | 1단계 |

#### 작동 원리 [A]

MM은 **실제 속도**로 포즈를 고른다("내려는 속도"가 아니라). 벽에 막혀 실제 속도가 0이면 걷는
클립을 재생하는 게 아니라 제자리 포즈를 고른다. 이것이 `titan_example`의 속도 정규화 버그
(설계 문서 1.3절)가 구조적으로 발생할 수 없는 이유다.

#### 궤적 [A]

`PoseSearchGenerateTrajectory(forCharacter)`가 캐릭터의 이동 상태에서 궤적을 만든다.
**AI 구동에서도 동일 경로로 동작한다** — 자체 궤적 생성기 불필요.

AI가 손대야 하는 것은 정확히 2개:
- `PreviousDesiredControllerYaw` ← 위협/조준 방향
- `TrajectoryGenerationData_Moving` / `_Idle` ← AI 회전 특성에 맞게 재튜닝 **[C-1]**

#### 스키마 [A]

궤적 5샘플(−0.05 / 0 / +0.35 / +0.70 / +1.0초, 미래 1초의 가중치가 1.5로 최대) +
포즈 4특징(발 상대위치 1.0, 양발 속도 0.3, 골반 헤딩 0.1). **상체 특징이 하나도 없다** →
조준을 애디티브로 얹어도 매칭이 흔들리지 않는다.

#### 데이터 요구사항 [A]

새로 들여오는 모든 로코모션 클립은:
1. **루트모션 포함** (없으면 MM 불가)
2. **`contact_l`/`contact_r` 커브 보유** (없으면 발 배치 오작동 — 분석 문서 3.3b절)
3. UE5 Manny 스켈레톤

#### 열린 질문

- **[C-1]** AI 구동 시 `TrajectoryGenerationData` 값. 특히 급선회에서 예측 궤적이 실제 회전을
  못 따라가면 엉뚱한 포즈를 고른다. **판정: 위협 방향으로 급선회할 때 포즈가 튀지 않는가**

### 6.2 자세 높이 (Stance Height) ★ 가장 비싼 축

| 항목 | 내용 |
|---|---|
| **타입** | **연속** 0..1, 단 앵커 구간별로 성질이 다름 |
| **분류** | 목표=결정(L2), 현재값=수렴(L4) |
| **생성** | 앵커 포즈 보간 + 스프링-댐퍼 동역학 + 발 IK 보정 |
| **파이프라인** | 2단계 (IK 구간, FootPlacement 앞) |

#### 구조 — 앵커 + 구간 모드 [A]

**하나의 0..1 축이 아니라 "앵커 목록 + 구간 속성"이다.** 이래야 나중에 Prone을 추가해도
기존 코드가 안 바뀐다.

```cpp
USTRUCT()
struct FStanceAnchor
{
    FGameplayTag  Tag;                // Stance.Stand / Crouch / Prone
    float         Height;             // 1.0 / 0.35 / 0.08
    float         MaxSpeedScale;      // 이 자세에서의 최대 이동속도 배율
    float         CapsuleHalfHeight;
    // 이 앵커에서 유효한 애디티브 세트(조준 오프셋 등)
};

UENUM()
enum class EStanceIntervalMode { Interpolable, RequiresTransition };

USTRUCT()
struct FStanceInterval             // 인접한 두 앵커 사이
{
    EStanceIntervalMode Mode;
    // RequiresTransition일 때만: 긴급도별 전이 클립
};
```

**1차 범위:**
```
Stand(1.0) ──[Interpolable]── Crouch(0.35)
```
**2차 확장:**
```
Stand ──[Interpolable]── Crouch ──[RequiresTransition]── Prone(0.08)
```
앵커 하나 + 구간 하나를 **데이터로** 추가하면 끝이다.

#### 왜 Stand↔Crouch는 순수 축인가 [A]

1. **지지 기반이 안 바뀐다** — 양발이 계속 접지. 구성 공간이 연속이고 연결돼 있다
2. **중단 가능성이 결정타다** — 0.35로 내려가는 중 위협이 발생하면 목표값을 0.9로 바꾸면 끝.
   전이 클립이면 중간에 끊고 되돌리는 지저분한 처리가 필요하다. 연속적으로 판단을 바꾸는
   AI에게 "동작이 끝날 때까지 기다리기"는 곧 기계적인 느낌이다
3. 다른 축과 거의 독립적이다(예외 3개는 아래)

#### 왜 Crouch↔Prone은 전이인가 [A]

**지지 기반이 발 → 몸통 전체로 바뀐다.** 선형 보간하면 몸이 공중에 뜬 중간 상태가 나온다.
물리적으로 의미가 없다.

#### 속도는 별도 축이 아니다 — 축 자체가 동역학을 갖는다 [B]

"빠르게 털썩 / 느리게 조심스럽게"를 전이 클립으로 풀 필요가 없다.

```
CurrentHeight ← 2차 스프링-댐퍼
    target     ← AI (Posture.TargetHeight)
    stiffness  ← f(Posture.Urgency)     급할수록 높음
    damping    ← f(Posture.Urgency)     급할수록 낮음 → 오버슈트 후 정착 = "털썩"
    maxRate    ← f(부상, 하중, 피로)
```

- 급함: 높은 강성 + 낮은 감쇠 → 빠르게 내려가 **살짝 지나쳤다가 튀어 올라 정착**
- 조심스러움: 높은 감쇠 → 매끄럽게 도달
- **클립 0개, 중단 항상 가능**

> **[B] 근거**: 원리는 명확하나 오버슈트 양과 강성/감쇠 매핑은 튜닝 대상. 과하면 만화처럼 보인다.

#### 보간이 못 주는 것 (경계) [A]

- **손 접촉이 들어가는 하강**(벽을 짚고 내려앉기) — 접촉점이 생기면 보간 불가
- **지지 기반이 바뀌는 자세**(Prone) — 2차로 분리한 이유
- **발 재배치가 필요한 깊은 스쿼트** — 전투 웅크림은 발을 안 옮기므로 해당 없음

#### 결합 3가지 [A]

| 결합 | 내용 |
|---|---|
| **캡슐 높이** | 축을 따라가야 함. `SetCapsuleHalfHeight` 연속 구동 → 바닥 스냅/충돌 해소 영향. **이 축의 실제 구현 비용** |
| **최대 이동속도** | `MaxSpeed = f(Height)`. 웅크린 채 전력질주 불가 |
| **애디티브의 앵커별 버전** | 조준 오프셋이 Stand용 21 + Crouch용 21로 존재. 축 0.5면 **둘을 블렌드**. → **앞으로 추가하는 모든 애디티브는 앵커마다 버전이 필요하다** |

세 번째가 미래 비용의 원천이므로 지금 못박는다.

#### MM DB 선택은 여전히 이산이다 [A]

포즈 높이는 연속이지만 **데이터베이스 선택은 이산**이다. 서서 걷기(452)와 웅크려 걷기(431)는
발 딛는 패턴 자체가 다른 별개 데이터셋이라 "중간 데이터베이스"가 없다.

```
포즈 높이    : 연속 (축)
MM DB 선택   : 이산 (Chooser + 히스테리시스, 임계 ~0.6)
경계 흡수    : Inertialization
```

선택된 DB의 포즈 위에 높이 축이 변형을 얹는다. 서서 걷기를 0.5로 낮추면 "무릎 굽히고 걷는"
모습이 나오는데, 반쯤 웅크린 이동이 실제로 그렇게 보이므로 수용 가능할 것으로 본다.

#### 열린 질문

- **[C-2]** **블렌드 구간(0.4~0.7) 품질.** MM이 선 자세 보폭에 맞는 포즈를 골랐는데 골반을
  낮추면 보폭이 안 맞아 `FootPlacement`가 다리를 늘리거나 미끄러뜨릴 수 있다.
  **판정: 높이를 0→1로 천천히 스윕하며 걸을 때 발 미끄러짐/다리 늘어남이 있는가**
- **[C-3]** 캡슐 연속 구동 시 바닥 스냅/충돌 해소가 안정적인가
- **[C-4]** `Phase` 커브를 이용한 DB 경계 위상 정합이 실제로 매끄러운가

### 6.3 몸 방향 · 조준 · 시선 (Facing / Aim / Gaze)

**세 개의 서로 다른 회전이며 절대 하나로 합치면 안 된다.**

| 회전 | 정의 | 결정/수렴 | 소스 |
|---|---|---|---|
| **이동 방향** | 속도 벡터의 방향 | 결과값. 아무도 직접 정하지 않음 | CMC |
| **몸 방향** | 액터/루트 회전 | 목표=결정, 현재=수렴 | CMC 회전 설정 |
| **조준 방향** | 무기가 향해야 할 방향 | 목표=결정(표적), 현재=수렴(L4) | AIController 컨트롤 로테이션 |
| **시선 방향** | 머리/눈 | 결정(무엇을 볼지) + 자율(스캔) | Look-At 솔버 |

#### 몸 방향 모드 [A]

GASP의 `E_RotationMode`를 그대로 쓴다.

| 모드 | 몸이 향하는 곳 | 병사 상황 |
|---|---|---|
| `OrientToMovement` | 이동 방향 | 순찰, 비접촉 이동, 총 내림 |
| `Strafe` | 고정(컨트롤러) | 접촉 중 이동 — 몸은 위협, 다리는 이동 방향 |
| `Aim` | 조준 방향 | 정조준 |

**AI 배선**: CMC의 `bOrientRotationToMovement` / `bUseControllerDesiredRotation` 플래그 전환.

#### 조준 오프셋 [A]

```
AOValue = Delta( aimingRotation , RootTransform.rotation )
```

**조준각 = 조준 방향 − 시각적 루트 방향.** 몸이 돌면 오프셋이 자동으로 줄어든다.
`RootTransform`은 캡슐이 아니라 `OffsetRootBone`이 만든 시각적 루트다(분석 문서 5.2절).

**억제 메커니즘 [A]**: 애니메이션에 `Disable_AO` 커브를 넣으면 그 구간만 조준 오프셋이 꺼진다.
**데이터가 시스템을 제어하는 패턴이고 우리도 채택한다** — 트래버설·전이·재장전 클립에 사용.

#### 조준 한계각과 재정렬(re-plant) [B]

Orientation Warping은 **하체를 180°까지** 커버하지만 그건 "몸 방향 대비 이동 방향"의 범위다.
**조준 방향 자체가 몸 뒤로 넘어가는 경우는 워핑이 풀어주지 않는다.** 사람도 허리를 90° 넘게
비틀 수 없어 발을 다시 딛는다.

각도 구간별 처리(`몸통 정면 → 조준 목표`의 Yaw 차이):

| 구간 | 처리 | 담당 |
|---|---|---|
| **0~45°** (`AimDeadzone`) | 몸통 그대로, Aim Offset + CR 보정만 | L4 |
| **45~90°** (`AimTwistMax`) | 상체 비틀기 + 몸통을 천천히 목표로 보간 | L4 + L3 |
| **90° 초과** | **재정렬 트리거** — L3가 "몸통 재정렬" 태스크 발행. 정지 중이면 turn-in-place, 이동 중이면 pivot을 MM이 선택 | L3 판단 / L4 수행 |
| **135° 초과 + 즉시 대응** | 급선회 우선, 그동안 **사격 보류**(조준 수렴 조건이 자동으로 막음) | L3 |

**설계 규칙 3가지 [A]**

1. **재정렬은 L4가 몰래 하지 않는다.** 몸통을 트는 건 사격 가능 여부를 바꾸므로 L3 태스크로
   표현한다. 그래야 "지금 돌고 있어서 못 쏜다"가 판단 레이어에 보인다
2. **재정렬 중에는 조준 수렴 타이머가 리셋된다.** 몸을 홱 돌려 즉사시키는 것이 구조적으로 불가능해진다
3. **한계각은 자세마다 다르다.** Prone은 상체 비틀기 여유가 거의 없어 `AimTwistMax`가 훨씬 작고
   재정렬 비용이 크다

#### 시선은 조준과 분리한다 [A]

**베이스: GASP 5.8의 Look-At POI 솔버**(Control Rig, **additive**, 신체 부위별 추적 강도 개별
제어). 기존 애니메이션을 덮어쓰지 않는다 — 5.5.1절의 실패를 반복하지 않는 핵심 성질.
샘플에 **순찰 NPC 스캔 방향 제어** 데모가 포함돼 있어 우리 인지 시스템(설계 문서 7.2절)의
시야 스캔과 그대로 맞물린다.

**확장**: 대상이 "바라볼 지점"이 아니라 **"총구가 향해야 할 지점"**인 변형을 하나 더 만들고,
체인을 spine→clavicle→upperarm으로 잡아 총구 소켓을 최종 이펙터로 삼는다.

> 상태: 실험적(Experimental). **복사해서 우리 리그로 가져와** 쓰고 GASP 원본 갱신에 종속시키지 않는다.

#### 열린 질문

- **[C-5]** 견착 자세에서 Orientation Warping이 몇 도까지 버티는가 (P0-2). 필요 클립 수가
  2방향/4방향/8방향으로 갈린다
- **[C-6]** `AimDeadzone`/`AimTwistMax` 실제 값

### 6.4 무기 자세 (Weapon Posture)

| 항목 | 내용 |
|---|---|
| **타입** | **이산** (앵커 상태) + 전환 |
| **분류** | 결정(L2/L3) |
| **파이프라인** | 3단계 (애디티브 앵커) |

#### 앵커 목록 [B]

| 앵커 | 설명 | 조준 오프셋 필요? |
|---|---|---|
| `Lowered` | 총구 아래, 비전투 휴대 | ❌ (시선 오프셋만) |
| `LowReady` | 견착하되 총구 약간 아래, 경계 | ❌ (또는 축소판) |
| `ADS` | 정조준, 개머리판 견착 | ✅ **전용 세트 필요** |
| `Hip` | 허리 사격 | ⚠️ IK 변형으로 대체 가능 |
| `Blind` | 엄폐물 밖으로 팔만 내밀어 사격 | ⚠️ **IK 주도** (아래) |
| `Reload` / `Malfunction` | 전환 동작 | ❌ (몽타주, `Disable_AO`) |

#### 맹목사격(Blind Fire)은 IK 주도다 [B]

임의 방향으로 팔만 내밀어 쏘는 것은 앵커를 다 만들 수 없다. **FullBodyIK**로 무기를 목표
트랜스폼에 고정하고 팔 체인을 풀되, 척추는 stiffness로 부분 추종시킨다.

- **한계**: 극단 구성에서 고무처럼 보인다
- **완화**: 가장 가까운 앵커 포즈로 블렌드해서 IK 해가 그럴듯한 영역에 머물게 한다

#### 데이터베이스 확장 방법 [A]

분석 문서 7.3절: DB 선택은 `MovementMode × Stance × MovementState × Gait` 이산 조합표다.
**`WeaponPosture` 컬럼을 하나 추가하면 된다. 코드 수정 없이 데이터만으로 확장된다.**

#### 열린 질문

- **[C-7]** `LowReady`에 별도 조준 오프셋이 필요한가, `ADS` 세트의 축소 적용으로 충분한가
- **[C-8]** 맹목사격 IK의 품질 하한

### 6.5 좌우 기울기 (Lean)

| 항목 | 내용 |
|---|---|
| **타입** | 연속 −1..1 |
| **분류** | 목표=결정(엄폐 슬롯이 요구), 현재=수렴 |
| **생성** | **절차적** — Control Rig 척추 롤 + 캡슐 오프셋 |
| **앵커** | 불필요(절차적). GASP에 `BS1D_Additive_Lean_Run`(가속 뱅킹) 선례 존재 |
| **파이프라인** | 2단계 |

**주의**: GASP의 lean은 **가속에 따른 뱅킹**(자동)이고, 우리가 필요한 것은 **엄폐물 밖으로
몸을 기울이는 의도적 lean**이다. **두 개는 다른 축이며 둘 다 필요하다.**

```
Lean_Banking   자율   ← 가속도                     (GASP 기존)
Lean_Tactical  결정   ← 엄폐 슬롯 / 사격 각도 확보  (신규)
```

- **[C-9]** 두 lean이 동시에 걸릴 때 합성 방식(합산 / 우선순위 / 클램프)

### 6.6 교란 — 호흡 · 떨림 · 반동 잔여 (Disturbance)

| 항목 | 내용 |
|---|---|
| **타입** | 연속, 작은 진폭 |
| **분류** | **자율**. 변조 입력만 AI가 제공 |
| **생성** | **Control Rig 연산** (애디티브 아님 — 5.4절 공간 문제) |
| **파이프라인** | 6단계 (안정화 IK 뒤, 결합 IK 앞) |

#### 호흡 [B]

```
BreathPhase(t) : 기본파 + 노이즈, 개체별 위상 offset (동기화 방지)
    주기  ← f(Speed2D, 피로, 부상, 긴장)
    진폭  ← f(같은 것) × (1 − 숨참기)
영향 부위: 흉곽 상하, 어깨 미세 상하, 그 결과 총구가 흔들림
```

**호흡이 조준을 틀어지게 하는 것이 정상이다.** 총은 몸이 들고 있으므로 가슴이 움직이면 총구가
따라 움직인다. 7단계 결합 IK는 왼손을 총열에 붙여둘 뿐 총구 방향을 되돌리지 않는다.

#### 떨림 / 반동 잔여 [B]

```
Tremor    ← f(피로, 부상, 저체온, 긴장) — 고주파 저진폭
Recoil    ← 발사 이벤트에서 감쇠 진동 (무기별 파라미터)
Suppression flinch ← 근접 탄착 이벤트 (설계 문서 7·9절의 피제압도)
```

#### 열린 질문

- **[C-10]** 각 교란의 진폭이 게임플레이에 쓸 만한 탄착 오차를 만드는가(5.5절)
- **[C-11]** 45명이 동시에 호흡할 때 Control Rig 비용

### 6.7 반응 — 피격 · 피제압 (Reaction)

2.2절대로 **"맞은 순간"과 "다친 상태"를 분리**한다.

#### 피격 강도별 처리 [B]

| 강도 | 처리 | 이유 |
|---|---|---|
| **경미** (원거리 피탄, 방탄복 흡수) | **애디티브 상체 플린치**를 MM 위에 얹음. MM 계속 | 로코모션을 끊으면 오히려 부자연스럽다 |
| **중간** (유효타, 부상 발생) | **전용 히트리액션 MM DB로 Chooser 스왑** (방향별) | 몽타주로 강제하면 이동 중 발이 미끄러진다. DB 스왑이면 궤적 연속성 유지 |
| **치명/사망** | MM 완전 이탈 → 사망 몽타주 또는 래그돌 | 애니메이션 관할 밖 |
| **넉백/폭발** | PhysicsControl 물리 반응 후 MM 복귀 | 2차 |

**중간 강도가 핵심 결정이다.** `titan_example`은 몽타주 기반이라 슬롯 배선 문제로 "죽는 모션이
안 나오는" 버그를 겪었다. MM DB 스왑은 슬롯 경합 자체가 없다.

#### 권한 채널 — 이 명세의 핵심 개념 [A]

다리에 맞았을 때 필요한 것은 "포즈를 하나 더 얹는 것"이 아니라 **발 고정의 권한을 뺏는 것**이다.

```
각 단계는 두 채널을 받는다:
    포즈 기여 (무엇을 더할 것인가)
    권한 계수 (얼마나 덮어쓸 수 있는가)      ← 이것이 없으면 표현 불가
```

`FootPlacement`는 이미 `unplantRadius`/`unplantAngle`/`speedThreshold`로 접지 해제 조건을 갖고
있다. 여기에 부상 상태를 물려 **alpha를 낮추거나 끊으면** 발이 미끄러지고, 완전히 끊으면
8단계 물리로 넘어가 무너진다.

#### 부상 상태 모델 [A]

```
Healthy → Injured → Downed → Dead
```

| 상태 | 신체 | 판단(설계 문서 8.3절 축) |
|---|---|---|
| `Injured` | 이동속도↓, 조준 수렴 시간↑, 정확도 콘↑, 절뚝임 DB 스왑 | `TakeCover`/`Retreat`↑, `Advance`↓, 분대 사기 감소 |
| `Downed` | 이동/사격 불가, 포복만 | 주변 아군의 `Revive` 점수↑ |

## 7. 필요 앵커 데이터 총량 산정 [B]

**이 명세의 가장 실용적인 결론이다.** 조달 요청을 "클립 몇 개"가 아니라 "축별 앵커 N개"로

### 7.1 핵심 관찰

**조준 공간 전체가 42개 정지 포즈로 정의된다.** 로코모션 1,450개의 3%다.

그리고 이것들은 **로코모션 클립이 아니라 정지 포즈**다 — 루트모션도, 접지 커브도, 보행 위상도
필요 없다. **디자인팀이 "제작"할 수 있는 난이도가 완전히 다르다.**

> 조달 요청을 이렇게 바꿀 수 있다:
> ~~"라이플 견착 로코모션 클립 수백 개"~~ → **"라이플 견착 정지 포즈 42개 + 무기 자세 앵커 3개"**

### 7.2 남은 진짜 구멍 — 2026-09-03 확정 [A]

**Orientation Warping이 무엇을 커버하고 무엇을 못 커버하는지가 확정됐다**(분석 문서 16.2절,
Epic의 그래프 주석에 명시).

| 카테고리 | 워핑이 커버? | 필요 데이터 |
|---|---|---|
| **정상상태 루프**(직선 이동) | ✅ **커버함** — "전진 보행 하나로 여러 각도 스트레이프" | **전방 위주 소수 클립으로 충분** |
| **start / stop / pivot / turn-in-place** | ❌ **구조적으로 못 함** — 워핑은 직선 구간에서만 동작하며 `Enable_Warping` 커브로 게이팅됨 | **데이터 필수. 여기가 진짜 비용** |

즉 [C-5]의 답이 "몇 도까지 버티는가"가 아니라 **"어떤 종류의 동작을 커버하는가"**로 나왔다.
루프는 해결되고, **전환이 남는다.**

`../assets/2026-09-02_asset_supply_and_collaboration.md` 5절의 A/B/C안은 이제 **전환 카테고리에만**
적용하면 된다 — 범위가 크게 좁아졌다.

### 7.3 반입 클립 필수 커브 3종 [A]

우리가 들여오는 모든 로코모션 클립은 다음을 가져야 한다. **없으면 해당 시스템이 조용히
오작동한다.**

| 커브 | 용도 | 없으면 | 생성 |
|---|---|---|---|
| `contact_l` / `contact_r` | 발 심기 타이밍 (`FootPlacement`) | 발이 미끄러지거나 계속 심김 | `UMotionExtractorModifier` (TranslationSpeed) |
| **`Enable_Warping`** | 워핑 허용 구간 (Orientation Warping) | **워핑이 영원히 안 켜짐 → 방향 커버 0** | 루트 RotationSpeed 기반 (P0-4에서 검증) |

| 도구 | 플러그인/명령 | 보여주는 것 |
|---|---|---|
| **Rewind Debugger** | `GameplayInsights` (표시명 **Animation Insights**) — 모듈 `RewindDebugger`, `RewindDebuggerRuntime`, `RewindDebuggerVLog` | **최근 구간을 되감아 프레임 단위로 재생.** 애님 노드 활성 상태·변수 값·비주얼 로그를 타임라인으로. **순간적으로 지나가는 문제를 잡는 유일한 방법** |
| **Pose Search Debugger** | `PoseSearch` 플러그인의 Editor 모듈 | **MM이 무엇을 왜 골랐는지** — 후보별 검색 비용, 채널별 비용 분해, 선택된 클립/시간. Rewind Debugger 안에 통합됨 |
| **StateTree Debugger** | `StateTree` | 활성 상태 경로, 태스크 상태, 전환 발생 이력 |
| `showdebug animation` | 콘솔 | 애님BP 노드 트리·활성 몽타주·커브 값 화면 표시 |
| **GASP `DDCvar.DrawCharacterDebugShapes 1`** | GASP 내장 | 궤적·발 접지 등 디버그 도형. **실측 결과 조준 회전 시 발이 60°마다 재배치되는 것이 이걸로 보였다** |

**규칙**: 새 디버그 기능을 만들기 전에 위 도구로 되는지 먼저 확인한다. 특히 **Pose Search
Debugger는 우리가 만들 수 없는 정보(채널별 비용 분해)를 준다.**

### 12.2 우리가 만들어야 하는 것 — 엔진이 못 보여주는 것 [B]

엔진 도구는 "엔진이 아는 것"만 보여준다. **우리 파이프라인의 축과 판단은 우리가 만들어야 한다.**

#### ① 병사 HUD (선택/근접 시 화면 표시)

```
┌─ Soldier_03  [Veteran]  ─────────────────────────────┐
│ Intent   AimedFire  (0.72)   ← TakeCover 0.61, Reload 0.44
│ Posture  height 0.35→0.35  urgency 0.2   anchor Crouch
│ Facing   mode Aim   body 142°  aim 147°  Δ5°
│ Weapon   ADS   converged 0.8s   muzzle-target Δ1.2°
│ Feet     L planted(0.4s)  R swing        contact 0.02/0.91
│ Disturb  breath 0.31 (T=3.4s)  tremor 0.05  recoil 0.00
│ State    Healthy  suppress 0.15  ammo 21/30
│ MM       PSD_Dense_Crouch_Walk_Loops / M_Neutral_..._F_LL  cost 0.83
└──────────────────────────────────────────────────────┘
```

**설계 원칙: HUD의 항목이 곧 `FSoldierPoseIntent`의 필드와 축 목록이다.** 새 축을 추가하면
HUD에도 한 줄이 자동으로 는다 — 별도로 만들지 않는다.

#### ② 총구 궤적 트레일 ★

최근 N초간 **총구 소켓의 월드 위치를 선으로** 그린다.

**5.5절(탄착 오차를 난수로 만들지 않는다)의 검증 수단이다.** 호흡·떨림·이동이 실제로 얼마나
오차를 만드는지 눈으로 봐야 [C-10]을 판정할 수 있다. 표적 방향 기준 각도 오차를 함께 수치로 표시.

#### ③ 파이프라인 단계별 기여도

```
1 로코모션 베이스   MM: PSD_..._Walk_Loops
2 자세 변형         height 0.35   lean 0.00
3 무기 앵커         ADS  (alpha 1.0)
4 조준 오프셋       yaw +12.4  pitch -3.1
5 안정화 IK         gain 0.72   (숙련 0.9 × 부상 1.0 × 피로 0.8)
6 교란              breath 0.31  tremor 0.05   → 총구 편차 1.2°
7 결합 IK           foot alpha 1.0 / 1.0   hand-grip alpha 1.0
8 물리              inactive
```

각 단계의 **alpha·gain·권한 계수**를 나열한다. 5.1절의 "권한 계수" 개념이 눈에 보이게 된다.
피격으로 발 IK 권한이 떨어지는 순간을 이 화면에서 확인할 수 있어야 한다.

#### ④ 축 값 시계열 그래프

주요 축(자세 높이, 조준 오차, 호흡 위상, 총구 편차)을 **작은 실시간 그래프**로. 스프링-댐퍼
튜닝(6.2절)은 수치만 봐서는 못 한다 — 오버슈트 모양을 봐야 한다.

### 12.3 구현 방침 [B]

| 항목 | 방침 |
|---|---|
| 위치 | `Source/SoldierLab/Debug/` (설계 문서 3.7절 — 1급 시민) |
| 표시 대상 | 한 번에 1명(선택된 병사) + 전체 요약. 45명 전부 그리면 아무것도 안 보인다 |
| 토글 | 콘솔 변수로 항목별 on/off (GASP의 `DDCvar.*` 패턴 답습) |
| 성능 | **디버그 수집은 표시 중일 때만.** 상시 수집하면 12.2절 예산을 먹는다 |
| 기록 | 상세 기록은 Rewind Debugger에 위임. 우리는 실시간 표시에 집중 |

### 12.4 언제 만드는가 [A]

**P1 초반, 축을 구현하기 전에 HUD 골격부터 만든다.**

근거: 유틸리티 튜닝([C-14])과 스프링 파라미터 튜닝([C-2], 6.2절)은 **값이 보여야 가능하다.**
UI 없이 축을 늘리면 이전 프로젝트와 같은 상태("왜 저렇게 움직이는지 아무도 모름")가 된다.
