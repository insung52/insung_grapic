답변드리는 내용은 파란색 볼드처리하여 표시하였습니다.

 

 

1. 요청↔응답 상관관계 (프로토콜 세부)
 
메시지 봉투(`{cmd,src,recv,data}`)에 순번(seq)이나 요청ID가 없습니다. 예를 들어 저희가  `RC_Request_BIT`를 보내고 `UGV_Response_BIT`가 오기 전에 원격통제기가 또 다른 `RC_Request_BIT`를 보내면, 어느 응답이 어느 요청에 대한 것인지 구분할 방법이 없습니다.
그래서 저희는 **"같은 cmd는 이전 응답을 받은 뒤에만 다음 요청을 보낸다(한 번에 하나씩 순차 처리, 서로 다른 cmd끼리는 동시 처리 가능)"**는 규칙으로 구현하려고 합니다. 원격통제기 쪽도  이 전제(같은 cmd는 순차 재요청만)로 만들어졌는지, 아니면 응답을 기다리지 않고 같은 cmd를  여러 번 한꺼번에 보낼 수 있는 구조인지 확인 부탁드립니다.
        --> 원격통제기는 응답을 기다리지 않고 같은 cmd를 여러 번 한꺼번에 보낼 수 있는 구조로 되어있습니다. 동일한 request가 들어오더라도 그 즉시 해당되는 response를 보내주시면 됩니다.
 
2. UDP 비주기 명령 유실 시 확인/재시도 메커니즘 (우선순위 높음 — 안전 관련)
 
1 )배경 : UDP는 전송 계층에서 순서보장·재전송·수신확인이 전혀 없습니다.
           ICD가 명시하는신뢰성 메커니즘은 주기성 메시지(Request/Response, 응답 없으면 재시도)와 이벤트 메시지 (  message/ACK, 3회 재시도) 두 가지뿐인데,
           RC→UGV 커맨드 대부분이 이 중 어느 쪽으로도 명시적 편입이 안 되어 있고(cmd 자체는 "비주기"로만 표기, 대응 응답 cmd 없음),
           특히 아래 두 개는 유실 시 위험도가 다른 명령들과 차원이 다릅니다.
2) RC_EmergencyStop : 유실되면 비상정지 명령이 UGV에 아예 안 들어감. 단일 실패 지점 중 가장 위험.
3) RC_FireWeapon`의 `RELEASE`(방아쇠 뗌) : `PRESSED`(사격) 유실은 "안 쏨"으로 fail-safe지만, `RELEASE` 유실은 "방아쇠 뗐는데 계속 쏨" — 오발/폭주 사격 시나리오.
 

※ 2번 문의 질의 사항
 
    질의사항 1
    - `RC_EmergencyStop`/`RC_EmergencyStopRelease`에 전용 응답(ACK) cmd가 없는데, 원격통제기가 수신/실행 여부를 어떻게 확인하나요?

     (a) 저희 쪽에 새 응답 cmd ( ex : `UGV_Response_EmergencyStop`) 추가를 요청드려도 되는지,
     (b) 아니면 원격통제기가 이미 다른 방식(예: 반복 송신, 또는 Q3의 `OperationMode` 필드 감시)으로 확인하고 있는지 알고 싶습니다.
        --> (b) 안이 맞습니다. 주기적으로 OperationMode에 대한 값이 변경되는 형태 입니다.
 
    질의사항 2
   - `RC_FireWeapon`의 `PRESSED`/`RELEASE`가 매 프레임 반복 전송되는 값인가요, 아니면  버튼 상태가 바뀌는 시점에만 1회 전송되는 이벤트인가요?

     후자라면 `RELEASE` 유실 시 UGV가 계속 사격 상태로 남을 위험이 있는데, 이에 대한 별도 안전장치(발사 지속시간 상한, watchdog 타임아웃 등)이 이미 있는지 확인 부탁드립니다.
     없다면 저희 쪽에 "일정 시간 갱신 없으면 자동 정지" 워치독을 자체적으로 넣는 걸 검토 중입니다.
        --> 점사 및 연사 구현을 위해서 실제 신호는 pressed/release 두 신호 모두 조이스틱에서 이벤트가 발생할때마다 전송합니다 프레임 단위로 전송은 하지 않습니다.
             - 단발시 UGV에서 PRESSED 신호를 수신시 격발 RELEASE 신호 수신시 재격발 가능 상태로 천이

             - 점사시 PRESSED 신호 수신시 3회 격발 RELEASE 신호 수신시 재격발 가능 상태로 천이

             - 연사시 PRESSED 신호 수신시 지속 격발 RELEASE 신호 수신시 격발 중지 및 재격발 가능상태로 천이

           상기 로직으로 보시면 될것 같습니다 우려하시는 RELEASE 신호 유실시 사격 상태로 남겨지는 내용은 현재 진행한 사업에서는 고려하지 않고 개발된것으로 알고 있습니다.

 

   질의사항 3

   - `RC_Control_Right`/`RC_OperationMode`도 전용 ACK는 없지만, UGV가 `UGV_Period_Basicinfo`(10Hz)로 `ConrtrolRight`/`OperationMode` 값을 계속 방송합니다.
     원격통제기가 이 주기 필드를 명령 반영 여부 확인 수단으로 써서 필요 시 재전송하는 구조인가요? 그렇다면 저희 쪽 별도 ACK 요청은 불필요합니다.
        --> 네, 말씀해주신 방식이 맞습니다.

    질의사항 4
   - `RC_EmergencyStop`과 `RC_OperationMode=EMERGENCY`가 같은 상태를 가리키는 건지
     (`RC_EmergencyStop` 수신 시 UGV가 `OperationMode`를 `Emergency`로 전환해 10Hz 방송에 반영하는지), 아니면 독립된 별개 개념인지 확인 부탁드립니다.
     전자라면 Q1의 확인 수단으로 `OperationMode` 필드를 그대로 쓸 수 있습니다.
        --> ICD상의 오기입이 있었습니다. UGV_Period_Basicinfo의 OperatioMode는 RC_EmergencyStop과 RC_EmergencyStopRelease를 통하여 설정/해제가 됩니다.

    질의사항 5
   - `RC_SelectCamera`/`RC_FireMode`/`RC_ChargeWeapon`은 유실 시 조작자가 인지한
     설정과 실제 UGV 상태가 어긋날 수 있는데, 현재 상태를 확인할 주기 필드/응답 cmd가 ICD에 안 보입니다.
     누락된 건지, 원격통제기 UI에서 별도로 상태를 보여주는 방식이 있는지 확인 부탁드립니다.
        --> 실 체계에서는 상태를 확인하는 응답 필드가 있습니다만, 데모를 위한 ICD를 간소화 하기 위하여 고의로 삭제하였습니다. 


3. 자율주행(HAD/FAD) 목적지 명령이 ICD에 안 보임
 
`UGV_Period_Basicinfo.OperationMode`엔 `FAD`(종속주행)/`HAD`(자율주행) 값이 있어서 "지금 자율주행 중"이라는 **보고**는 가능한데,
그 반대 방향인 `RC_OperationMode`엔 `STAY`/`REMOTE`/ `EMERGENCY` 세 값뿐이고 `FAD`/`HAD`로 전환시키는 커맨드가 없습니다.
"이 좌표로 자율주행해서 접근해라" 같은 목적지/미션 명령 자체가 RC→UGV 방향 전체에 안 보입니다.
 
※ 3번 문의 질의 사항
 
    질의사항 1
    - 자율주행 목적지/미션은 원격통제기가 전혀 관여하지 않고 UGV/ADU가 스스로(또는 사전 입력된 경로로) 판단해서 움직이는 구조인가요?
      아니면 상위체계가 원격통제기를 거쳐 UGV에 미션을 전달하는 경로가 실제로 있나요?
        --> 실제는 상위체계에서 이동좌표를 전달하는 실제로 존재합니다. 시나리오상 LLM이 전송한 이동경로에 대해서 UGV로 던지는 내용이 추가될 수도 있을 것 같은데 해당 내용은 차후 논의 해보면 될것 같습니다 

            역으로 문의드리고 싶은 건이 있습니다. RPG게임에서 목적지를 지정하면 자동으로 경로를 만들어주는 것 같은 기능이 Unreal에 내장되어있는지 확인 요청드립니다.

 
    질의사항 2
   - UGV에 미션을 전달하는 경로가 있다면 그 커맨드 이름/필드가 무엇인가요?
     저희는 확답 받기 전까지 임시로 `HQ_Missi onmoveToEngage`(`East`/`North`/`Zone`/`Letter`+`Radius`, 예전 상위체계 연동 초안에서 가져온 이름)를 기존 RC 채널(8000~8011)에 얹어서 쓰고 있는데,
     정식 스펙이 확인되면 그걸로 교체하겠습니다.
        --> 해당 내용은 정의가 필요한 사항으로, LIG에서 결정되는대로 공유드리겠습니다.
 
 
 
4. `RC_ActivateFire`/`RC_ActivateMovement`/`RC_MotionMode` 용도 확인
 
세 커맨드 다 값 패턴이 `*Toggle, RELEASE=활성/PRESSED=비활성`로 동일해서, 설명("발사 상태 설정"/"구동 상태 설정"/"기동 모션 모드 설정")만으로는 정확한 용도를 특정하기 어려웠습니다.
확답 받기 전까지 이렇게 추정해서 우선 구현해뒀습니다:
 
- `RC_ActivateFire` = 사격계통 안전/암(Arm) 스위치 — 꺼지면(SAFE) 배럴 정지+방아쇠를 당겨도  발사 안 됨, 켜지면(ARM) 배럴이 미리 워밍업돼서 이후 방아쇠는 스핀업 딜레이 없이 즉시 발사.
        --> 조정간 안전 이라고 보시면 될것 같습니다
- `RC_ActivateMovement` = 구동계 시동/이그니션 — 꺼지면 엔진음 정지+주행 명령 전부 무시,  켜지면 다시 조작 가능.
        -- > 해당 기능은 RCWS의 조향 관련으로 활성시 조향가능 비활성시 조향불가로 이해하시면 될것 같습니다
- `RC_MotionMode` = 아직 미구현(용도를 특정 못해서 로그만 남기는 스텁 상태).
        --> 해당기능은 차후에 논의 대상으로 남겨두어야 할것 같습니다
 
 
※ 4번 문의 질의 사항
 
    질의사항 1
   -위 두 추정(`RC_ActivateFire`/`RC_ActivateMovement`)이 맞는지, `RC_MotionMode`의 정확한 용도는 무엇인지 확인 부탁드립니다.
        --> 위의 명령 값 별 답변드린내용 참고 부탁드립니다.
 
 
 
5. `RC_RemoteDriving`/`RC_Request_BIT` 등을 주기 포트로 보내는 게 맞는지 (포트 분류)
 
ICD 시트1은 단말별로 주기 포트(8000/8010)와 이벤트 포트(8001/8011) 두 개를 확정했는데, "어느 cmd가 어느 포트로 가야 하는지"를 명시한 표는 못 찾았습니다.

저희는 시트3의 "주기"컬럼에 Hz 값이 적혀있는 것
(`RC_RemoteDriving`=20Hz, `RC_Request_BIT`/`RC_Request_BIT_ADU`=1Hz)만 주기 포트로, 나머지 "비주기"로 표기된 것 전부를 이벤트 포트로 보내는 걸로 가정하고 구현했습니다.
 
※ 5번 문의 질의 사항
 
    질의사항 1
   -이 포트 분류 가정이 맞는지 확인 부탁드립니다.
        --> 말씀해주신 분류 가정이 맞습니다.
 
 
 
6. `ObjectClass`(Human/Car) 판정 기준
 
`Objects[]`의 `ObjectClass`가 `Human`/`Car` 두 값뿐인데, 저희 쪽 판정 로직은 단순히 "사람 캐릭터인지 여부"만 봅니다. 트럭/UGV/민간 차량 등이 전부 다 `Car`로만 분류됩니다.
 
 
※ 6번 문의 질의 사항
 
    질의사항 1
   - 이 정도 단순 이분류로 충분한지, 아니면 차량 종류를 더 세분화해서 보고해야 하는지 확인 부탁드립니다.
        --> 말씀해주신 트럭/UGV/민간 차량의 구분이 가능하시면 구분해서 보내주셔도 되고, Car로만 구분해서 보내주셔도 됩니다.
 
 
 
7. `Gear` 필드의 `Turn`(제자리선회) 값
 
`UGV_Period_Basicinfo.Gear`에 `Front`/`Back`/`Turn` 세 값이 있는데, 저희 UGV(Chaos 휠드 물리 기반)가 실제로 궤도 2개로 제자리선회가 가능한 하드웨어를 흉내내고 있는 건지,
맞다면 `Turn` 상태를 판정하는 기준(예: 좌우 조향은 큰데 전진 입력은 거의 없는 상태)이 있는지 불확실합니다. 지금은 `Front`/`Back`만 판정해서 보내고 `Turn`은 절대 안 나갑니다.
        --> 실 무기체계에서는 제자리 선회 기능이 있으나, 이번 건에서는 제자리 선회 상태값은 안보내주셔도 됩니다.
 
 
8. `RC_Movement`의 `BrakeButton` 해석이 맞는지
 
`RC_Movement`(RCWS 조준 관련)의 `BrakeButton` 필드를 "RCWS 팬/틸트 모션 브레이크"로 해석해서 구현했습니다.
다만 ICD의 "활성/비활성"이 브레이크 자체를 가리키는 게 아니라 **회전(모션)이 활성/비활성이라는 뜻**으로 재해석했습니다: 
`RELEASE`(브레이크 풀림) = 회전 활성(정상적으로 `XAxis`/`YAxis`가 마운트를 움직임), `PRESSED`(브레이크 눌러서 걸림) = 회전 비활성(조준 이동 입력 전부 무시).
실제 짐벌/포탑 장비에 흔한 "브레이크를 눌러야 고정, 떼면 자유롭게 움직임" 개념으로 추정했는데, 확정된 건 아닙니다.
 
※ 8번 문의 질의 사항
 
    질의사항 1
   - 위 해석(RELEASE=브레이크 풀림→회전 활성, PRESSED=브레이크 걸림→회전 비활성)이 맞는지 확인 부탁드립니다. 아니라면 정확한 의미도 같이 확인 부탁드립니다.
        --> ActivateMovment는 RCWS의 조향 모터를 활성, 브레이크는 락의 개념이라 RC_ActivateMovement가 활성(RELEASE) AND RC_Movement의 BrakeButton이 활성(RELEASE)인 경우에 RCWS의 제어가 가능합니다.

 
 
이 외에 추가로 궁금하신 사항이 있으시다면 편하게 연락주시면 감사드리겠습니다.
