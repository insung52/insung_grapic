## 0. 한눈에 보기 (2026-08-07 LIG 답변 반영 갱신)

- **우리가 만드는 SW는 실질적으로 2개**: **UGV 시뮬레이션 SW**, **자체방호 통제기 SW**
  (이동형지휘소, 단일 프로그램 — 아래 §1.5 참고). **원격통제기(UGV축 콘솔)와 상위체계는
  LIG가 만듦** — "타사가 만들 수도"가 아니라 LIG 시스템 구성도(2026-08-06)에 회색(LIG SW)으로
  명시된 확정 사실. 다만 우리도 화면 전달/기본 동작 확인용 **최소 테스트 클라이언트**는
  만든다(§1.5).
- **3계층이 아니라 사실상 2계층**: (B) UGV 시뮬레이션 SW ↔ 원격통제기(LIG) — **UDP+JSON,
  실제 IP/포트 확정**(§2). (C) UGV 시뮬레이션 SW ↔ 자체방호 통제기SW — 언리얼 네이티브
  리플리케이션, 계획 유지(2026-08-07 재확인, §1.3). **(A) 상위체계 연동은 LIG도 아직
  미정** — "자체방호통제기→상위체계 ICD 정의 안 됨, 추가 여부 LIG 검토중"(§3).
- **자체방호(이동형지휘소)축은 에뮬레이터+콘솔 분리가 아니라 단일 프로그램** — 조이스틱이
  바로 꽂히고 그 안에서 시뮬레이션+제어+RTSP 송출까지 다 함(2026-08-07 확정, 이전 결정
  철회, §1.5).
- **전송계층: UDP로 통일 확정 (2026-08-07, 팀장님과 논의 완료).** NATS는 폐기 — UGV축이
  이미 LIG 방식(UDP+JSON)으로 확정된 마당에 내부적으로 NATS를 따로 유지할 이유가 없다고
  판단. 앞으로 생길 수 있는 Layer A도 확정되면 같은 UDP+JSON 패턴을 따를 가능성이 높음(§3).
  트랙2(NATS 인프라)는 완료된 채로 보류 — 당장 걷어내진 않되 추가 투자 안 함.
- **UDP는 유실을 전제로 설계해야 함** — TCP(NATS)와 달리 전달 보장이 없어서, LIG가 이미
  스펙에 애플리케이션 레벨 ACK+재시도를 내장해뒀음(§2). **Postman 같은 HTTP 중심 도구로는
  UDP 테스트가 안 됨** — 별도 테스트 도구/전략 필요(§8).
- 지휘통제플랫폼 서버랙(운용/GPU/빅데이터/가시화서버) 얘기는 이번 LIG 답변에 안 나옴 —
  여전히 미확인 상태(§6).

```
                    [상위체계] (LIG SW)
                   /                  \
      RTSP:CCTV/RCWS영상          (프로토콜 미정 — §3, LIG도 검토중)
             /                          \
   [자체방호 통제기 SW]              [원격통제기] (LIG SW, 우리 미제작)
   (단일 프로그램, 우리 제작)              |  UDP+JSON, IP/포트 확정(§2)
   USB 조이스틱 직결                       ↓
                                   [UGV 시뮬레이션 SW] (우리 제작)
                                          ↕
                    (C) 언리얼 리플리케이션, 계획 유지(2026-08-07 재확인)
                                          ↕
                          자체방호 통제기 SW ⟷⟷⟷ UGV 시뮬레이션 SW
```

## 1. Layer C — UGV 시뮬레이션 SW ↔ 자체방호 통제기 SW (언리얼 네이티브 리플리케이션)

**2026-08-07: LIG 시스템 구성도엔 이 둘을 잇는 링크가 안 그려져 있었으나, 사용자 확인
결과 "당연히 같은 가상환경에서 돌아가야 하니 계획 유지"로 확정.** 다만 다이어그램에
없었던 이유(생략인지 진짜 없는 건지)는 여전히 불명확 — 여유 있을 때 LIG에 재확인 권장.

### 1.1 코드베이스: `titan_example` 하나, 런타임 모드 선택

두 프로세스는 **같은 프로젝트/실행파일**에서 나옴 — RCWSComponent, 차량 물리, 리플리케이션
세팅 등 공유 코드를 두 곳에서 따로 관리하지 않기 위함. 패키징 시 또는 실행 시 "축(UGV/
자체방호)"을 선택. **2026-08-07부로 두 축의 역할이 더 벌어짐**: 자체방호 모드는 로컬
UI+조이스틱 입력 처리까지 이 프로세스 안에서 담당(§1.5), UGV 모드는 원격통제기(LIG)를 향한
UDP+JSON 서버 + RTSP 서버 역할이 중심(로컬 UI는 디버그용으로만 필요할 수 있음, 프로덕션
콘솔은 LIG 쪽).
(이건 "프로세스는 분리, 코드는 공유"라 §4-1 분리 우선 원칙과 안 부딪힘.)

### 1.2 토폴로지: 리슨서버, UGV PC가 기본 호스트, 런타임 선택 가능

- **전용서버(Dedicated Server) 방식은 폐기.** 에뮬레이터라는 개념 자체가 "현실을 대체"하는
  것이라, 실제로는 둘을 중계하는 제3의 서버가 존재할 자리가 없음 + 서버랙에 여유 자원이
  진짜 있을지도 불확실 — 존재 여부가 불확실한 하드웨어에 의존하는 설계는 피함(§4-5).
- **리슨서버**: 자체방호 PC가 7개 씬, UGV PC가 5개 씬을 렌더링 — 부하가 더 적은 **UGV PC를
  기본 호스트**로 함.
- **호스트/클라이언트도 런타임 선택 가능하게**: "축 선택"과 같은 패턴으로 시작 시점에
  호스트/클라이언트 역할도 고를 수 있게 구현(언리얼의 `?Listen`/`<IP>` 맵 URL 메커니즘).
  부수 효과: 리슨서버는 클라이언트가 안 붙어도 싱글플레이처럼 동작해서 한쪽 PC만 켜고 솔로
  개발/테스트도 자연스럽게 됨.

### 1.3 리플리케이션 대상

- 아군/적군 45명 캐릭터(이동/애니메이션/체력/사망 — 표준 `CharacterMovementComponent`
  리플리케이션으로 대부분 커버, 커스텀 상태만 `Replicated`+`OnRep` 추가), UGV/트럭 차량
  상태(Chaos Vehicle 네트워크 프리딕션, UE5.1+ 기본 지원 확인 필요).
- **RCWS 발사**: 액터 리플리케이션 안 함. **히트스캔 + Multicast RPC** — 서버가 판정, 결과만
  멀티캐스트로 뿌려서 각 클라이언트가 로컬로 트레이서/이펙트 스폰. (감사 결과: 현재
  `ARCWSProjectile`는 실제로 날아가는 풀링 Actor라 이 방향으로 마이그레이션 필요, §1.4 참고.)
- **아군 30명은 UGV에 종속된 로컬 팔로워 개념** — 별도 통신 없이 UGV 에뮬레이터 내부 AI
  로직으로 처리.
- **UAV도 리플리케이션 대상에 포함** (2026-08-06 확정) — UGV 쪽 화면에서도 UAV가 보여야
  "하나의 배틀필드 공유" 취지에 맞음.
- **감사 완료** (`replication_audit.md`, 2026-08-06): `RCWSComponent`/`RCWSFireControlComponent`,
  `UGVMovementComponent`/`UGVAIController`, `titan_examplePlayerController`, 아군/시나리오
  스폰 시스템 — 결과는 §1.4.

### 1.5 자체방호축 / UGV축 — 콘솔 구조 (2026-08-07 전면 수정)

**자체방호(이동형지휘소)축: 단일 프로그램으로 확정.** 이전엔 UGV처럼 "에뮬레이터+원격통제
장치 네트워크 분리"로 통일하려 했으나, LIG 시스템 구성도가 "이동형 지휘소 SW = UAV 제어 +
자체방호 RCWS 모사"를 한 박스로 묶어놨고 조이스틱이 그 프로세스에 USB로 직결됨을 확인 —
**이 방향으로 계획 변경.** 즉 자체방호 통제기 SW 안에 시뮬레이션 + 조이스틱 입력 처리 +
로컬 UI(필요하면) + RTSP 송출(상위체계 방향)이 전부 한 프로세스에 있음. 별도 콘솔
프로세스/프로토콜(Layer B) 자체가 없어짐 — 예전 §2(자체방호축 NATS 프로토콜) 설계는 폐기.

**UGV축: 원격통제기는 LIG가 제작.** 우리가 만드는 건 "UGV 시뮬레이션 SW"뿐. 원격통제기와의
인터페이스는 §2의 확정 스펙(UDP+JSON)을 그대로 구현해서 맞추면 됨 — 우리가 프로토콜을
설계할 필요 없음(이미 LIG가 정해서 알려줌). 다만 **우리도 테스트용 최소 클라이언트를
만들어야 함**(2026-08-07 확정) — 목적은 "화면(RTSP 영상)이 잘 전달되는지", "UDP+JSON
왕복이 되는지" 정도의 기본 동작 확인이지, 프로덕션 수준 UI/조이스틱 통합이 아님. 이전에
계획했던 "통제기SW 플러그인 계층화"(공통 플러그인+축별 프로젝트)는 이 축소된 목적에 맞게
훨씬 가벼운 스코프로 진행 — RTSP 수신 뷰어 + 기본 UDP/JSON 송수신 정도의 디버그 툴 수준.

## 2. UGV축 인터페이스 — UGV 시뮬레이션 SW ↔ 원격통제기(LIG) — **외부 확정 스펙**

**이건 우리 설계 선택이 아니라 LIG가 이미 구현한 원격통제기에 맞춰야 하는 외부 제약.**
2026-08-06 LIG 답변으로 확정, 상세 필드는 `protocol_icd.md` §3(전면 개정).

- **전송**: UDP, JSON 문자열. IP/포트 확정:

  | 단말 | IP | Port(주기) | Port(비주기) |
  |---|---|---|---|
  | UGV | 192.168.10.10 | 8000 | 8001 |
  | 원격통제기 | 192.168.10.20 | 8010 | 8011 |

- **메시지 봉투**: `{ cmd, src, recv, data: {...} }` — 우리가 짰던 `{cmd,seq,ts,payload}`
  형식이 아니라 LIG 형식을 그대로 따라야 함. device 코드: `RC=20`, `UGV=14`,
  `UGV_RCWS=13`, `UGV_ADU=12`.
- **신뢰성은 NATS/JetStream이 아니라 애플리케이션 레벨 ACK+재시도**(`image.png`,
  `문의내용0806.md` 첨부): 주기성 메시지는 응답 없으면 N회까지 Request 재시도, 이벤트
  메시지는 `( )msec` 내 ACK 없으면 3회까지 Message 재시도.
- 영상은 RTSP 그대로 유효(§7의 자체 구현 방향 안 바뀜) — "시뮬레이션이 RTSP 서버가 되어
  필요한 곳에서 스트리밍"이라고 명시돼 있어 우리가 세운 "UE NVENC+gst-rtsp-server" 방향과
  합치.
- LIG가 "정의에 따른 데이터 송수신 모듈은 내일 중 전달"이라고 했음 — 실제 cmd 코드
  목록/데이터 송수신 참조 구현이 곧 옴, 도착하면 §3 전체를 그걸로 다시 맞춰야 함(현재는
  봉투 포맷/IP포트/device코드만 확정, cmd 값 목록은 우리 추정치).

## 3. Layer A — 자체방호 통제기SW ↔ 상위체계 — **미정, LIG도 검토중**

2026-08-06 LIG 답변: *"자체방호통제기에서 상위체계로 가는 ICD 정의는 안되어있고, 향후 추가
여부도 LIG 검토중."* 시스템 구성도에도 이 방향 화살표 자체가 없음(RTSP 영상 업로드만
있음). **즉 우리가 앞서 설계한 HQ_/RPT_ 메시지 체계(교전승인 게이트, 시나리오 #4-1~4-8
체인)는 "확정 스펙 구현"이 아니라 "LIG가 이 채널을 추가하기로 하면 바로 쓸 수 있는 선제
설계"로 위상이 낮아짐.**

폐기하지 않음 — 여전히 유효한 사전 작업(`protocol_icd.md` §5, 트랙3 `hq_stub/`) — 다만
우선순위는 확정 스펙(§2)보다 낮춤. 설계 원칙(교전승인 게이트, 판단/보고 원칙, §4의 원칙
1~4)은 계속 유효.

### 판단/보고 게이트 원칙 (Layer A가 언젠가 생긴다면 적용)

> **위험하거나 비가역적인 행동(발사/교전)에만 승인 게이트를 넣는다.** 저위험/가역적
> 행동(정찰, 이동, 카메라·짐벌 조작)에는 안 넣음. "판단"과 "보고"는 다른 카테고리.

**교전승인 게이트**: `RCWSFireControlComponent`에 `bEngagementAuthorized`(기본값 off/토글
가능) — Remote 수동격발/AutoFire 자동사격 둘 다 이 플래그를 체크. **Layer A 확정 전까지는
이 게이트를 꺼둔 채로 나머지 기능을 테스트**(오히려 지금 상황과 잘 맞음 — 상위체계 연동
자체가 미정이니 당연히 꺼둔 채로 감).

### 시나리오 단계별 메시지 체인 요약 (전체는 `protocol_icd.md` §5)

#4-1(침투보고) → #4-2(정찰) → #4-3(식별, FYI보고) → #4-4(이동명령) → #4-5(도착, FYI보고) →

## 4. 재사용 가능한 설계 원칙 모음

1. **분리 우선(구조적 경계에 한함)**: 나중에 합치는 게 나중에 분리하는 것보다 항상 쌈 —
   프로세스/네트워크 경계처럼 되돌리기 비싼 결정은 분리를 기본값으로. (2026-08-07 참고:
   자체방호축은 이 원칙과 별개로 "원래부터 합쳐진 게 맞았다"는 게 LIG 확인으로 드러난
   경우 — 원칙 자체가 틀린 게 아니라 그때 정보가 부족했던 것.)
2. **자동 vs 게이트**: 위험/비가역 행동에만 승인 게이트, 나머지는 즉시 실행 + FYI 보고.
3. **트리거 소스와 이벤트 처리 로직 분리**: 실물 연동 전엔 콘솔 명령/디버그 버튼으로 스텁,
   나중에 신호 소스만 교체.
4. **기존 함수/enum에 올라타기**: 새 프로토콜 명령은 가능하면 이미 구현된 함수 시그니처에
   매핑.
5. **되돌리기 싼 결정은 나중으로 미룬다**: (2026-08-07 수정) 단, 이 원칙은 **우리가 실제로
   선택권을 가진 링크에만** 적용됨 — UGV축↔원격통제기처럼 외부(LIG)가 이미 구현해버린
   링크는 "미루기"가 아니라 그냥 그쪽 스펙을 따라야 함. (사후 판단: 이번엔 결국 미루지
   않고 바로 결정하는 쪽이 나았음 — 내부 NATS 유지 여부도 "일단 미루자"보다 외부 제약에
   맞춰 UDP로 바로 통일하는 게 더 단순했음. 원칙은 유효하되, "미룰 가치가 있는지"도 매번
   판단 필요.)
6. **불확실한 하드웨어에 의존하지 않는다**: 스펙을 계속 못 받는 상황이라, "어딘가에 여유
   자원이 있을 것" 같은 가정 위에 설계하지 않음(전용서버 폐기 사례).

## 8. UDP 테스트 도구/전략 (2026-08-07 신규)

**Postman은 HTTP/REST/WebSocket/gRPC 중심이라 raw UDP를 못 다룸** — 다른 방법 필요.

- **1순위: 자체 Python UDP 테스트 스크립트.** 트랙3(`hq_stub/`)에서 이미 검증한 패턴(파이썬
  으로 프로토콜 클라이언트 짜서 시나리오 체인 재생)을 그대로 UDP+`{cmd,src,recv,data}`
  봉투에 적용 — `socket` 모듈로 UDP 송수신은 몇 줄이면 됨. LIG의 재시도/ACK 시퀀스
  (`protocol_icd.md` §3.1)까지 구현해두면, 이게 곧 **트랙6(UGV축 최소 테스트 클라이언트)**의
  핵심이 됨 — 별도 도구가 아니라 트랙6과 같은 작업.
- **2순위(보조, GUI로 빠르게 한 방 테스트할 때)**: Packet Sender(무료 GUI, UDP/TCP 송수신)
  같은 범용 툴 — 프로토콜 로직(재시도 등) 검증엔 안 맞고 "일단 패킷 하나 보내지는지"
  확인용.
- **와이어 레벨 검증엔 Wireshark 필수** — 실제로 어떤 바이트가 나가는지/오는지 캡처해서
  LIG 원격통제기와 포맷이 정확히 맞는지 확인. `UGV` IP(192.168.10.10) 필터로 캡처하면 됨.
- **`hq_stub/`(트랙3)은 NATS 기반이라 이번 UDP 테스트엔 그대로 재사용 못 함** — Layer A가
  나중에 확정되면 그때 UDP 버전으로 포팅. 지금 당장은 새로 짜는 트랙6 스크립트가 우선.
