## 1. 발송 대상 질문 (현재 — 2026-08-28 기준 남은 것만)

### 1-신규-1. `RC_OperationMode=EMERGENCY` 레거시 송신 가능성

LIG 답변으로 ICD의 `RC_OperationMode` 값 중 `EMERGENCY`는 오기입이고, 실제로는
`RC_EmergencyStop`/`RC_EmergencyStopRelease`만이 `OperationMode`를 `Emergency`로
전환시킨다고 확인받았습니다(§3 참고). **후속 질문**: 실제 원격통제기 소프트웨어가 이 오기입
때문에 관성적으로 `RC_OperationMode=EMERGENCY` 값을 실제로 보낼 가능성이 있는지 확인
부탁드립니다 — 저희 쪽은 방어적으로 그 값이 오면 무시하거나 `RC_EmergencyStop`과 동일하게
처리해두려 하는데, 실제로 안 올 값이라면 그 방어 코드 자체가 불필요해서 여쭤봅니다.

### 1-신규-2. UGV 차량(구동계) 시동/이그니션 관련 커맨드 존재 여부

`RC_ActivateMovement`가 저희 예상과 달리 "RCWS 조향 모터 활성화"였다는 걸 확인받았습니다
(§3 참고). 그러면 **UGV 차량 자체(주행부)의 시동/이그니션 on-off에 대응하는 별도 커맨드가
ICD에 있는지** 궁금합니다 — 지금 저희가 이해하기로는 `RC_Control_Right`(제어권)와
`RC_OperationMode`(STAY/REMOTE)만으로 주행 가능 여부가 결정되고, 차량 엔진 자체의
시동/정지라는 개념은 프로토콜에 없는 것으로 보이는데 맞는지 확인 부탁드립니다.

### 1-신규-3. "시나리오상 LLM이 전송한 이동경로" 관련 확인

3번 문의 답변에서 "시나리오상 LLM이 전송한 이동경로에 대해서 UGV로 던지는 내용이 추가될
수도 있을 것 같다"고 하셨는데, 여기서 말씀하신 "LLM"이 상위체계(지휘통제 시스템)를 가리키는
것인지, 아니면 실제로 LLM(대규모 언어모델) 기반 경로 생성 컴포넌트를 가리키는 것인지 확인
부탁드립니다 — 후속 설계에 영향을 줄 수 있어서 여쭤봅니다.

### 1-1. 요청↔응답 상관관계 (프로토콜 세부)

메시지 봉투(`{cmd,src,recv,data}`)에 순번(seq)이나 요청ID가 없습니다. 예를 들어 저희가
`RC_Request_BIT`를 보내고 `UGV_Response_BIT`가 오기 전에 원격통제기가 또 다른
`RC_Request_BIT`를 보내면, 어느 응답이 어느 요청에 대한 것인지 구분할 방법이 없습니다.
그래서 저희는 **"같은 cmd는 이전 응답을 받은 뒤에만 다음 요청을 보낸다(한 번에 하나씩 순차
처리, 서로 다른 cmd끼리는 동시 처리 가능)"**는 규칙으로 구현하려고 합니다. 원격통제기 쪽도
이 전제(같은 cmd는 순차 재요청만)로 만들어졌는지, 아니면 응답을 기다리지 않고 같은 cmd를
여러 번 한꺼번에 보낼 수 있는 구조인지 확인 부탁드립니다.

**[LIG 답변, 2026-08-28] 해소됨** — 원격통제기는 응답을 기다리지 않고 같은 cmd를 여러 번
한꺼번에 보낼 수 있는 구조. 동일한 request가 들어오더라도 그 즉시 해당 response를 보내주면
됨. → 우리 쪽 "순차 처리" 가정은 강제할 필요 없음, 매 요청 즉시 개별 응답(상태 없는 처리)
방식이 맞음 — UGV축 수신 로직이 실제로 그렇게 동작하는지 재확인 권장.

### 1-2. UDP 비주기 명령 유실 시 확인/재시도 메커니즘 (우선순위 높음 — 안전 관련)

**배경**: UDP는 전송 계층에서 순서보장·재전송·수신확인이 전혀 없습니다. ICD가 명시하는
신뢰성 메커니즘은 주기성 메시지(Request/Response, 응답 없으면 재시도)와 이벤트 메시지
(Message/ACK, 3회 재시도) 두 가지뿐인데, RC→UGV 커맨드 대부분이 이 중 어느 쪽으로도 명시적
편입이 안 되어 있고(cmd 자체는 "비주기"로만 표기, 대응 응답 cmd 없음), 특히 아래 두 개는
유실 시 위험도가 다른 명령들과 차원이 다릅니다.

- **`RC_EmergencyStop`** — 유실되면 비상정지 명령이 UGV에 아예 안 들어감. 단일 실패 지점
  중 가장 위험.
- **`RC_FireWeapon`의 `RELEASE`(방아쇠 뗌)** — `PRESSED`(사격) 유실은 "안 쏨"으로
  fail-safe지만, `RELEASE` 유실은 "방아쇠 뗐는데 계속 쏨" — 오발/폭주 사격 시나리오.

**질문**:

- **Q1.** `RC_EmergencyStop`/`RC_EmergencyStopRelease`에 전용 응답(ACK) cmd가 없는데,
  원격통제기가 수신/실행 여부를 어떻게 확인하나요? (a) 저희 쪽에 새 응답 cmd(예:
  `UGV_Response_EmergencyStop`) 추가를 요청드려도 되는지, (b) 아니면 원격통제기가 이미 다른
  방식(예: 반복 송신, 또는 Q3의 `OperationMode` 필드 감시)으로 확인하고 있는지 알고
  싶습니다.
- **Q2.** `RC_FireWeapon`의 `PRESSED`/`RELEASE`가 매 프레임 반복 전송되는 값인가요, 아니면
  버튼 상태가 바뀌는 시점에만 1회 전송되는 이벤트인가요? 후자라면 `RELEASE` 유실 시 UGV가
  계속 사격 상태로 남을 위험이 있는데, 이에 대한 별도 안전장치(발사 지속시간 상한, watchdog
  타임아웃 등)가 이미 있는지 확인 부탁드립니다. 없다면 저희 쪽에 "일정 시간 갱신 없으면
  자동 정지" 워치독을 자체적으로 넣는 걸 검토 중입니다(§2 참고).
- **Q3.** `RC_Control_Right`/`RC_OperationMode`도 전용 ACK는 없지만, UGV가
  `UGV_Period_Basicinfo`(10Hz)로 `ConrtrolRight`/`OperationMode` 값을 계속 방송합니다.
  원격통제기가 이 주기 필드를 명령 반영 여부 확인 수단으로 써서 필요 시 재전송하는
  구조인가요? 그렇다면 저희 쪽 별도 ACK 요청은 불필요합니다.
- **Q4.** `RC_EmergencyStop`과 `RC_OperationMode=EMERGENCY`가 같은 상태를 가리키는 건지
  (`RC_EmergencyStop` 수신 시 UGV가 `OperationMode`를 `Emergency`로 전환해 10Hz 방송에
  반영하는지), 아니면 독립된 별개 개념인지 확인 부탁드립니다. 전자라면 Q1의 확인 수단으로
  `OperationMode` 필드를 그대로 쓸 수 있습니다.
- **Q5.** `RC_SelectCamera`/`RC_FireMode`/`RC_ChargeWeapon`은 유실 시 조작자가 인지한
  설정과 실제 UGV 상태가 어긋날 수 있는데, 현재 상태를 확인할 주기 필드/응답 cmd가 ICD에
  안 보입니다. 누락된 건지, 원격통제기 UI에서 별도로 상태를 보여주는 방식이 있는지 확인
  부탁드립니다.

**[LIG 답변, 2026-08-28]**
- **Q1 해소** — (b) 맞음. `OperationMode` 필드가 주기적으로 반영됨 — 별도 ACK cmd 불필요.
- **Q2 해소, 중요** — PRESSED/RELEASE는 조이스틱 이벤트 발생 시에만 전송(프레임 단위 아님).

  삭제**했다고 함. 즉 이번 데모에서는 이 세 커맨드의 상태 확인 수단이 원천적으로 없음 —
  우리 쪽에서 별도로 확보할 방법 없음, 감수하고 진행.

### 1-3. 자율주행(HAD/FAD) 목적지 명령이 ICD에 안 보임

자율주행 중"이라는 **보고**는 가능한데, 그 반대 방향인 `RC_OperationMode`엔 `STAY`/`REMOTE`/
`EMERGENCY` 세 값뿐이고 `FAD`/`HAD`로 전환시키는 커맨드가 없습니다. "이 좌표로 자율주행해서
접근해라" 같은 목적지/미션 명령 자체가 RC→UGV 방향 전체에 안 보입니다.

- **Q6.** 자율주행 목적지/미션은 원격통제기가 전혀 관여하지 않고 UGV/ADU가 스스로(또는
  사전 입력된 경로로) 판단해서 움직이는 구조인가요? 아니면 상위체계가 원격통제기를 거쳐
  UGV에 미션을 전달하는 경로가 실제로 있나요?

### 1-4. `RC_ActivateFire`/`RC_ActivateMovement`/`RC_MotionMode` 용도 확인

세 커맨드 다 값 패턴이 `*Toggle, RELEASE=활성/PRESSED=비활성`로 동일해서, 설명("발사 상태
설정"/"구동 상태 설정"/"기동 모션 모드 설정")만으로는 정확한 용도를 특정하기 어려웠습니다.
확답 받기 전까지 이렇게 추정해서 우선 구현해뒀습니다:

- `RC_ActivateFire` = 사격계통 안전/암(Arm) 스위치 — 꺼지면(SAFE) 배럴 정지+방아쇠를 당겨도
  발사 안 됨, 켜지면(ARM) 배럴이 미리 워밍업돼서 이후 방아쇠는 스핀업 딜레이 없이 즉시 발사.
- `RC_ActivateMovement` = 구동계 시동/이그니션 — 꺼지면 엔진음 정지+주행 명령 전부 무시,
  켜지면 다시 조작 가능.
- `RC_MotionMode` = 아직 미구현(용도를 특정 못해서 로그만 남기는 스텁 상태).

- **Q8.** 위 두 추정(`RC_ActivateFire`/`RC_ActivateMovement`)이 맞는지, `RC_MotionMode`의
  정확한 용도는 무엇인지 확인 부탁드립니다.

**[LIG 답변, 2026-08-28]**
- **`RC_ActivateFire` 확인됨** — "조정간 안전"이라고 보면 됨. 우리 추정과 일치, 코드 변경 불필요.
- **`RC_ActivateMovement` 추정 틀림, 재매핑 필요** — "RCWS의 조향 관련으로 활성 시 조향 가능,
  비활성 시 조향 불가"로 이해하면 됨. 차량 시동/이그니션이 **아니었음**. `RC_Movement.
  BrakeButton`과 AND 조건(§1-8 답변 참고). `protocol_icd.md` §3.2에 반영, 코드 재배선은
  다음 UGV축 세션 착수 항목으로 등록.
- **`RC_MotionMode` 미해소** — "차후에 논의 대상으로 남겨두어야 할 것 같다" — 급하지 않음,

### 1-5. `RC_RemoteDriving`/`RC_Request_BIT` 등을 주기 포트로 보내는 게 맞는지 (포트 분류)

ICD 시트1은 단말별로 주기 포트(8000/8010)와 이벤트 포트(8001/8011) 두 개를 확정했는데,
"어느 cmd가 어느 포트로 가야 하는지"를 명시한 표는 못 찾았습니다. 저희는 시트3의 "주기"
컬럼에 Hz 값이 적혀있는 것(`RC_RemoteDriving`=20Hz, `RC_Request_BIT`/`RC_Request_BIT_ADU`
=1Hz)만 주기 포트로, 나머지 "비주기"로 표기된 것 전부를 이벤트 포트로 보내는 걸로 가정하고
구현했습니다.

- **Q9.** 이 포트 분류 가정이 맞는지 확인 부탁드립니다.

**[LIG 답변, 2026-08-28] 해소됨** — "말씀해주신 분류 가정이 맞습니다." 변경 불필요.

### 1-6. `ObjectClass`(Human/Car) 판정 기준

`Objects[]`의 `ObjectClass`가 `Human`/`Car` 두 값뿐인데, 저희 쪽 판정 로직은 단순히 "사람
캐릭터인지 여부"만 봅니다 — 트럭/UGV/민간 차량 등이 전부 다 `Car`로만 분류됩니다.

- **Q10.** 이 정도 단순 이분류로 충분한지, 아니면 차량 종류를 더 세분화해서 보고해야 하는지
  확인 부탁드립니다.

**[LIG 답변, 2026-08-28] 해소됨(선택 사항으로 확정)** — "트럭/UGV/민간 차량 구분이 가능하시면
구분해서 보내주셔도 되고, `Car`로만 구분해서 보내주셔도 됩니다." → 우리 쪽 판단으로 결정
가능. 우리가 실제 판별 가능한 항목은 §5(신규)에서 회신.

### 1-7. `Gear` 필드의 `Turn`(제자리선회) 값

`UGV_Period_Basicinfo.Gear`에 `Front`/`Back`/`Turn` 세 값이 있는데, 저희 UGV(Chaos 휠드
물리 기반)가 실제로 궤도 2개로 제자리선회가 가능한 하드웨어를 흉내내고 있는 건지, 맞다면
`Turn` 상태를 판정하는 기준(예: 좌우 조향은 큰데 전진 입력은 거의 없는 상태)이 있는지
불확실합니다. 지금은 `Front`/`Back`만 판정해서 보내고 `Turn`은 절대 안 나갑니다.

- **Q11.** 위 내용 확인 부탁드립니다.

**[LIG 답변, 2026-08-28] 해소됨(안 보내도 됨으로 확정)** — "실 무기체계에서는 제자리 선회
기능이 있으나, 이번 건에서는 제자리 선회 상태값은 안 보내주셔도 됩니다." → `Front`/`Back`만
판정해서 보내는 현재 구현 그대로 유지, 추가 구현 불필요(README `titan_example/README.md`
반영 완료).

### 1-8. `RC_Movement`의 `BrakeButton` 해석이 맞는지

`RC_Movement`(RCWS 조준 관련)의 `BrakeButton` 필드를 "RCWS 팬/틸트 모션 브레이크"로 해석해서
구현했습니다 — 다만 ICD의 "활성/비활성"이 브레이크 자체를 가리키는 게 아니라 **회전(모션)이
활성/비활성이라는 뜻**으로 재해석했습니다: `RELEASE`(브레이크 풀림) = 회전 활성(정상적으로
`XAxis`/`YAxis`가 마운트를 움직임), `PRESSED`(브레이크 눌러서 걸림) = 회전 비활성(조준 이동
입력 전부 무시). 실제 짐벌/포탑 장비에 흔한 "브레이크를 눌러야 고정, 떼면 자유롭게 움직임"
개념으로 추정했는데, 확정된 건 아닙니다.

- **Q12.** 위 해석(RELEASE=브레이크 풀림→회전 활성, PRESSED=브레이크 걸림→회전 비활성)이
  맞는지 확인 부탁드립니다. 아니라면 정확한 의미도 같이 확인 부탁드립니다.

**[LIG 답변, 2026-08-28] 해소됨, 단 조건 추가됨** — 우리 해석(RELEASE=회전 활성) 자체는
맞음. 다만 **`RC_ActivateMovement`가 RCWS 조향 모터 활성 스위치이고, 브레이크는 락 개념이라
`RC_ActivateMovement`=RELEASE(활성) **AND** `RC_Movement.BrakeButton`=RELEASE(활성)일 때만
RCWS 제어가 가능**하다고 확인됨 — 즉 우리가 지금 `BrakeButton`만으로 게이팅하던 걸
`RC_ActivateMovement`와의 AND 조건으로 확장해야 함(`protocol_icd.md` §3.2 반영 완료, 코드는
다음 UGV축 세션에서 재배선).

## 2. 답변 오기 전까지 우리 쪽 임시 대응 (LIG 질문 아님, 참고용)

**[2026-08-28] Q2 답변으로 "검토 중"→"구현 확정" 상태로 승격.** LIG가 "RELEASE 신호 유실 시
사격 상태로 남는 것은 현재 진행 사업에서는 고려하지 않고 개발된 것"이라고 명시적으로 확인 —
즉 LIG 쪽에도 이 시나리오에 대한 안전장치가 없음이 확정됨. 아래 워치독은 더 이상 "확인 전
임시 대응"이 아니라 **필수 구현 항목**.

- UGV 시뮬레이션 SW 자체에 `RC_RemoteDriving`/`RC_Movement`류 갱신이 일정 시간(예: 500ms~1s)
  끊기면 자동으로 안전 정지하는 워치독 구현.
- `RC_FireWeapon`도 동일 워치독 대상 포함 — 마지막 `PRESSED` 이후 일정 시간(예: 2-3초)
  넘게 갱신 없으면 자동 사격 중단(단발/점사는 자연 종료라 해당 없음, 연사만 실질적 위험).
- `RC_ActivateFire`를 사격계통 안전/암 스위치로 구현해둬서(§1-4), 안전 상태(SAFE)면
  `RC_FireWeapon`이 와도 무조건 무시하는 최소한의 안전장치는 이미 확보됨 — 다만 이건
  "안전을 걸어뒀는지"의 문제고, "`RELEASE` 패킷 자체가 유실되는"(안전이 이미 풀린 채로
  방아쇠 뗌 신호만 유실) 상황은 여전히 워치독으로 대응해야 함.

## 3. 해소된 것 / 자체 결정한 것 (질문 불필요, 기록용)

**ICD로 해소됨**:
- 좌표계: UTM(East/North/Zone/Letter) 확정, WGS84 아님.
- cmd 코드 전체 목록/data 필드: `lig_icd_ugv_rc_full.md`로 확정.
- device 코드(RC=20/UGV=14/UGV_RCWS=13/UGV_ADU=12) 실사용 여부: ICD 명시, 확정.
- Bounding Box 좌표 형식: 0~65535 정수 스케일링, 계산식까지 ICD 명시.

**자체 결정/해결(2026-08-16, 사용자 확인)**:
- **UTM Zone/Datum 정확한 값**: 질문 불필요 — 레벨디자인 끝나면 우리가 직접 위도/경도값
  기반으로 실제 위치를 1:1 매핑 가능.
- **`udp_test` 참조구현의 IP(`192.168.0.84`)/포트(`7777`/`7778`)가 임시값인지**: 질문
  불필요 — IP를 초기화면에서 커스텀 가능하게 개발할 예정이고 기본값은 실배포 스킴
  (`192.168.10.10` 등)으로 둘 것.
- **자체방호(이동형지휘소) 통제기 SW의 고정 IP**: 질문 불필요 — 위와 동일한 이유(커스텀
  가능하게 개발).
- **RTSP URL 임의 접속 가능 구조인지**: 질문 불필요 — 프로토콜을 이미 받았으므로 당연히
  가능할 것으로 가정.

**우리가 자체 결정한 것(기존)**:
- UGV/자체방호축 배틀필드 공유: 당연히 공유(리플리케이션) — 시스템 구성도에 링크가 안
  보였지만 우리 쪽 계획 그대로 유지.
- 재시도 횟수/타임아웃 값: 임의로 정하고 설정 가능하게 노출(`udp_protocol_client`의
  `RetryConfig`처럼) — LIG 확정값 안 기다림.

**LIG 1차 답변으로 해소됨(2026-08-28, `documents/response_0828.md`)**:
- 요청↔응답 상관관계: RC는 순차 대기 없이 동시 다중 요청 가능, 매번 즉시 응답하면 됨(§1-1).
- `RC_EmergencyStop`/Q1, `RC_Control_Right`/`RC_OperationMode` 주기 필드 확인 방식/Q3,
  포트 분류/Q9, `RC_ActivateFire`/Q8 — 전부 우리 가정/구현대로 확인됨.
- `RC_FireWeapon` PRESSED/RELEASE는 이벤트 단위 전송, 단발/점사(3회)/연사 로직 확인(Q2) —
  단 **RELEASE 유실 안전장치는 LIG도 없음이 확정**되어 워치독이 필수로 승격(§2).
- `RC_OperationMode`(STAY/REMOTE/EMERGENCY) ↔ 우리 `EUGVDriveMode` 매핑: **ICD의 EMERGENCY는
  오기입, 실제로는 STAY/REMOTE 두 값만 설정 가능하고 EMERGENCY는 `RC_EmergencyStop`/Release
  전용**(Q4) — `protocol_icd.md` §3.2에 매핑 확정 반영. 레거시 송신 가능성만 후속 확인(1-신규-1).
- `Gear=Turn`: 안 보내도 됨으로 확정(Q11) — `titan_example/README.md` 반영 완료.
- `ObjectClass` 세분화 여부: 우리 재량(Q10) — **2026-09-02 6값으로 확장 구현 완료**, LIG엔
  결정 통보만 남음(§5-2, 미발송).
- `RC_Movement.BrakeButton` 해석: 맞음, 단 `RC_ActivateMovement`와 AND 조건 추가 확인(Q12).

**LIG 1차 답변으로 새로 발견된 재작업 항목(질문 아님, 구현 수정 필요)**:
- **`RC_ActivateMovement` 재매핑** — 차량 시동/이그니션이 아니라 "RCWS 조향 모터 활성화"였음

  필요, `RC_Movement.BrakeButton`과 AND 조건으로 묶을 것 — 다음 UGV축 세션 착수 항목.

## 5. 이번에 LIG에 회신할 내용 (질문 아님, 우리가 답할 차례 — 2026-08-28 신규)

### 5-1. (3번 문의 답변 중 LIG의 역질문) NavMesh 기반 자동 경로 탐색 — Unreal 내장 여부

> *"RPG게임에서 목적지를 지정하면 자동으로 경로를 만들어주는 것 같은 기능이 Unreal에
> 내장되어있는지 확인 요청드립니다."*

**회신 초안**: 네, Unreal Engine에 NavMesh(내비게이션 메시) 기반 경로찾기가 엔진 기본
기능으로 내장되어 있고, 저희 프로젝트에도 이미 적용되어 있습니다. 목적지 좌표를 주면
NavMesh 위에서 자동으로 경로를 계산해서 따라가며(A* 기반), 저희 쪽은 여기에 더해 디자이너가
그려둔 특정 경로(스플라인)에 **가중치를 줘서 그 경로를 우선 따라가도록** 하는 기능도
추가로 구현해뒀습니다(`SplineNavModifierComponent` 활용). `RC_RemoteDriving`(수동 조향)과
자율주행 목적지 명령(현재 임시로 `HQ_MissionMoveToEngage`) 둘 다 이 경로 위에서 동작합니다.
자세한 구현은 `vehicle/ugv/2026-08-27_new_kadex_0811_navmesh_autonomous_driving.md`(내부 문서) 참고 가능.

### 5-2. (6번 문의 Q10 관련) `ObjectClass` 확장 — **결정 통보** (질문 아님)

> **상태**: 2026-09-02 구현 완료, LIG 통보만 남음(발송 필요). 답변 대기 항목 아님.

**회신 내용**: Q10 답변("트럭/UGV/민간 차량 구분이 가능하시면 구분해서 보내주셔도 되고,
`Car`로만 구분해서 보내주셔도 됩니다")대로 **저희 재량으로 판단해서 `ObjectClass`를 아래 6개
값으로 확장 구현했습니다**. 원격통제기 쪽에서 이 값들을 그대로 받아 표시해 주시면 됩니다.

| `ObjectClass` 값 | 의미 |
|---|---|
| `Ally` | 아군 보병 |
| `Enemy` | 적군 보병 |
| `UGV` | 무인차량(UGV) |
| `MobileCommandPost` | 이동형지휘소 |
| `Drone` | 정찰 드론 |
| `Parachute` | 적 강하 흔적(낙하산) |

ICD 원문의 `Human`/`Car` 두 값은 더 이상 나가지 않습니다. 계층 구조(`Human` 하위에
아군/적군, `Car` 하위에 UGV/이동형지휘소/드론) 대신 **평면 6값**으로 한 이유는 드론이
`Car`로 분류되기 어렵기 때문이고, 이번 시나리오에는 적 차량·적 드론이 없어 장비 3종은 항상
아군 자산이라 평면화해도 피아식별 정보가 누락되지 않습니다.

값 이름이나 형식을 바꿔야 하는 사정이 원격통제기 쪽에 있으면 알려주시면 맞추겠습니다.
