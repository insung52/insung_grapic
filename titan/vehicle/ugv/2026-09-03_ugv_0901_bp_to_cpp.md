## 2. ★ 죽은 노드 판정 — "연결된 노드"로 세면 안 된다

처음에 `get_connected_subgraph`(이벤트 노드에서 **모든** 연결을 타고 도달 가능한 노드)로 살아있는
집합을 구했더니 EventGraph 249개 중 **230개가 살아있는 것으로 나왔다.** 실제로는 4개다.

원인: 죽은 궤도 체인들이 **exec 선만 끊겼고 데이터 선은 아직 Tick 이벤트에 물려 있었다.**
`EventTick`의 `DeltaSeconds` 출력 핀 하나에 죽은 체인 10곳이 연결돼 있어서, 무향 그래프
도달성으로는 전부 "살아있음"이 된다.

**올바른 판정은 2단계다:**

1. 엔트리 노드(이벤트 / 함수 엔트리)에서 **exec 출력 핀만** 따라간 도달집합 = 실행되는 노드
2. 그 노드들의 **입력 핀**을 타고 거슬러 올라간 생산자들의 전이 폐포 = 그 실행에 필요한 순수 노드

이 둘의 합집합이 keep, 나머지가 고아다. `NodeInfo.output_pins[].type_id == "Exec"`로 exec 핀을
가려낼 수 있다.

> 이 판정을 눈으로 하면 안 된다. 249개 중 4개를 고르는 일이고, 데이터 선이 남아 있어서
> "이벤트에 연결돼 있으니 살아있겠지"가 통하지 않는다.

## 4. C++ 이관 — `AUGV0901Pawn`

`Source/titan_example/Vehicles/UGV0901Pawn.h/.cpp` 신규.

### 왜 `AUGVWheeledVehiclePawn`에 직접 안 넣었나

구형 궤도 UGV `BP_UGV_Vehicle_new`도 `AUGVWheeledVehiclePawn`을 부모로 쓴다. 그쪽은 아직 자기
EventGraph에서 `UpdateTurretVisuals`(총열 회전 포함)를 굴리고 있어서, 부모에 네이티브 Tick으로
같은 니아가라 파라미터를 쓰면 **한 프레임에 두 번 쓰게 된다.** 0901 계보만 받는 서브클래스를 두면
구형은 손댈 필요가 없다.

### 컴포넌트는 BP에 그대로 둔다

SCS 컴포넌트 22개(`RCWS`, `RCWSFireControl`, `BarrelSmokeFX`, `QuadCam`, 시네카메라 4개,
`RtspBridge`, …)의 위치·설정이 전부 BP 뷰포트에서 잡은 값이다. `CreateDefaultSubobject`로 옮기면
그 값을 전부 잃는다. C++는 BeginPlay에 한 번 찾아 캐시만 한다.

- `RCWS` / `RCWSFireControl` — 이 폰에 하나뿐이라 `FindComponentByClass`
- `BarrelSmokeFX` — 이 폰에 `UNiagaraComponent`가 여럿(`PathPreviewFX`, `AmbientFXAnchor`)이라
  **이름으로** 찾는다. `FComponentReference BarrelSmokeFXRef`, 기본값 `"BarrelSmokeFX"`
  (프로젝트의 `RCWSSightCineCamera`/`GimbalCineCamera` 관례와 동일)

### 이관 대응표

| BP | C++ |
|---|---|
| `SetManualControl(ForwardInput, TurnInput)` | 동명 `UFUNCTION` |
| `SetBraking(bNewBraking)` | 동명 `UFUNCTION` |
| `TurretYaw` / `GunPitch` | `BlueprintReadOnly` UPROPERTY (**double**, §5 참고) |
| Tick → `UpdateTurretVisuals` | `Tick()` → `UpdateTurretVisuals()` |
| 리터럴 0.5 / 0.5, 0.2 / 0.4 | `SmokeHeatThreshold`/`Range`, `HazeHeatThreshold`/`Range` (`EditAnywhere`) |
| `SmokeMaxSpawnRate`(28) / `HazeMaxSpawnRate`(5) / `HazeMaxDistortionStrength`(0.05) | 동명 `EditAnywhere`, 기본값 = 이관 전 CDO 값 |

과열 곡선은 그대로다 — 아지랑이가 열 0.2부터 올라와 0.6에서 최대, 연기는 0.5부터 시작.

### 건드리면 안 되는 이름 3종

1. **`SetManualControl` / `SetBraking`의 파라미터 이름** — `AUGVAIController::DispatchSetManualControl`이
   `Pawn->FindFunction()` + `Func->FindPropertyByName("ForwardInput")`로 값을 쓴다. 네이티브
   UFUNCTION이어도 이 경로는 그대로 동작하지만, 이름을 바꾸면 **컴파일은 통과하고 런타임에 입력만
   조용히 0이 된다.**
2. **`TurretYaw` / `GunPitch`** — `ABP_UGV_0901`이 `CastToBP_UGV_0901` 후 읽어
   `ModifyBone(Rotation_base2/RCWS3)`에 넣는다.
3. **C++ 멤버 이름이 BP 컴포넌트 이름과 겹치면 안 된다** — `RCWS`/`RCWSFireControl`/`BarrelSmokeFX`는
   BP의 컴포넌트 변수라, 같은 이름의 UPROPERTY를 부모에 두면 리페어런트 시 BP 컴파일이 이름
   충돌로 깨진다. 그래서 캐시 멤버는 `CachedRCWS` / `CachedFireControl` / `CachedBarrelSmokeFX`.

## 5. ★ 밟은 함정 — BP의 float은 double이다

리페어런트 후 `ABP_UGV_0901`이 컴파일 에러:

```
Turret Yaw of type Float (double-precision) doesn't match the property TurretYaw of type FloatProperty
Gun Pitch  of type Float (double-precision) doesn't match the property GunPitch  of type FloatProperty
```

옛 BP 변수 `TurretYaw`/`GunPitch`는 **double**(`FDoubleProperty`)이었는데 C++를 `float`로 잡았다.
UE5에서 블루프린트의 기본 float 타입은 실제로 double이다 — `AUGVAIController::DispatchSetManualControl`의
주석이 경고하는 것과 같은 정밀도 함정이고, 그쪽은 `FNumericProperty::SetFloatingPointPropertyValue`로
정밀도를 안 따지게 우회했지만 **프로퍼티를 BP가 직접 읽는 경우는 타입이 정확히 맞아야 한다.**

**해결: C++를 `double`로.** `FRotator::Yaw` 자체가 UE5에서 double이므로 오히려 축소 변환이 없어진다.

> 반대로 `SetManualControl(float, float)`은 `float`로 둬도 문제없다. 그쪽은 BP 노드가 아니라
> 리플렉션(`FNumericProperty`)으로만 불리기 때문이다. **BP가 핀으로 직접 읽는 프로퍼티만 double.**
