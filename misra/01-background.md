# 코드 검증(Verification) 기초 배경지식

> 목적: MISRA / ASIL 등 정적 분석·기능안전 검증 도구를 조사하기 전에 필요한 기본 개념 정리.
> 대상 컨텍스트: 그래픽 엔진(C/C++) 개발

---

## 1. 왜 이런 검증이 필요한가

소프트웨어가 사람의 안전이나 시스템 신뢰성에 영향을 줄 수 있는 분야(자동차, 항공, 의료, 산업 제어 등)에서는
"코드가 동작한다"는 것만으로 부족하고, **"코드가 특정 위험을 일으키지 않는다는 것을 증명할 수 있어야 한다**는 요구가 생긴다.

이를 위해 두 갈래의 활동이 존재한다.

- **코딩 표준 (Coding Standard)**: 언어 자체의 위험한 기능(미정의 동작, 묵시적 형변환 등)을 코드 작성 단계에서 차단.
  → 대표: **MISRA C / MISRA C++**
- **기능안전 표준 (Functional Safety Standard)**: 시스템/소프트웨어 개발 "프로세스" 전체가 위험을 얼마나 잘 통제하는지 규정.
  → 대표: **ISO 26262 (자동차)**, IEC 61508(산업 전반), DO-178C(항공), IEC 62304(의료기기)

MISRA는 "코드 레벨 규칙"이고, ASIL은 "ISO 26262 안에서 매기는 위험도 등급"이라서 서로 **레이어가 다르다.**
같은 선상에서 비교할 대상이 아니라, "ASIL이라는 요구수준을 만족시키기 위한 수단 중 하나가 MISRA 준수"인 관계다.

## 2. MISRA — 코딩 표준

### 2.1 정체
- MISRA(Motor Industry Software Reliability Association)가 만든 **C/C++ 코딩 가이드라인 모음**.
- 원래 자동차 업계에서 시작했지만, 지금은 항공·의료·산업기기 등 안전 critical 분야 전반과
  심지어 게임/그래픽 엔진처럼 "꼭 안전 규제 대상은 아니지만 신뢰성을 높이고 싶은" 분야에서도 참고용으로 많이 쓰임.
- 결과물은 "법"이 아니라 **가이드라인 문서(유료 PDF)** 다. 도구가 이를 구현해서 코드를 자동 검사해준다.

### 2.2 버전
| 표준 | 대상 언어 | 비고 |
|---|---|---|
| MISRA C:2012 (+ Amendment 1, 2, 3, 4) | C90/C99/C11/C18 | 가장 널리 쓰임 |
| MISRA C++:2008 | C++03 | 구버전, 여전히 많이 채택됨 |
| MISRA C++:2023 | C++17 | 최신, 사실상 새로 작성된 표준 |

그래픽 엔진은 보통 C++ 비중이 크므로, **MISRA C++:2008**(레거시 프로젝트) 또는 **MISRA C++:2023**(신규)이 주 관심사가 될 가능성이 높음.

### 2.3 규칙(Rule)의 구조
MISRA 규칙은 단순 "스타일 가이드"가 아니라 카테고리화되어 있다.

- **Rule vs Directive**
  - *Directive*: 코드만 봐서는 자동으로 검증하기 어려운, 절차/설계 관점 지침 (예: "요구사항이 추적 가능해야 한다")
  - *Rule*: 코드 자체를 보고 자동/반자동으로 검증 가능한 규칙 (예: "goto문 사용 금지")
- **분류 (Decidability)**
  - *Decidable*: 도구가 항상 명확히 판정 가능
  - *Undecidable*: 문맥/의도에 따라 판단이 갈릴 수 있어 도구가 false positive/negative를 낼 수 있음
- **준수 카테고리 (Category)**
  - **Mandatory**: 반드시 지켜야 함. 예외(deviation) 허용 안 됨.
  - **Required**: 지켜야 하지만, 정당한 이유가 있으면 공식적으로 "deviation(예외 처리)"을 기록하고 벗어날 수 있음.
  - **Advisory**: 권고 수준. 위반해도 무방하나 근거를 남기는 게 좋음.

이 "예외 처리(Deviation)" 프로세스가 실무에서 핵심이다. 100% 위반 0건을 목표로 하지 않고,
**위반을 모두 검출 → 검토 → 정당한 위반은 문서화하여 승인**하는 흐름으로 운영한다. 이를 위한 기능(Deviation Record, Suppression)을 지원하는지가 도구 선택 시 중요 기준이 됨.

### 2.4 예시로 보는 규칙의 느낌
- 묵시적 타입 변환으로 정보 손실 금지
- `union` 사용 금지/제한
- 동적 메모리 할당(`malloc`/`new`) 제한 (메모리 단편화·예측 불가능성 때문 — 그래픽 엔진의 실시간 메모리 관리와 직결되는 주제)
- 재귀 함수 제한 (스택 오버플로우 예측 불가능성)
- 함수 포인터/가상함수 사용 제약 (C++)
- 단일 `return` 지점 등 제어흐름 단순화

→ 그래픽 엔진 입장에서 부딫힐 만한 영역: 템플릿 메타프로그래밍, 멀티스레딩, SIMD intrinsic, 동적 할당, 예외 처리 등에서 MISRA와 충돌이 잦음 (MISRA C++:2023이 C++17 기능을 다루면서 이 부분을 상당히 현대화함).

## 3. ASIL과 ISO 26262 — 기능안전 표준

### 3.1 ISO 26262란
- 자동차 **전기/전자(E/E) 시스템**의 기능안전(Functional Safety)을 다루는 국제표준.
- "오작동으로 인한 위험을 시스템 개발 전 생애주기(요구사항→설계→구현→테스트→운영)에서 어떻게 관리하는가"를 규정.
- Part 6가 소프트웨어 개발에 해당하며, 여기서 코딩 표준 준수(=MISRA 등)를 권장/요구함.

### 3.2 ASIL이 뭔가
**ASIL (Automotive Safety Integrity Level)**: 특정 위험(Hazard)에 대해 "얼마나 엄격하게 안전을 보장해야 하는가"를 나타내는 등급.

- HARA(Hazard Analysis and Risk Assessment)라는 절차로, 사고 시나리오마다 3가지 요소를 평가해서 등급을 산정:
  - **S (Severity, 심각도)**: 사고가 발생했을 때 피해 정도
  - **E (Exposure, 노출도)**: 그 위험 상황이 실제로 발생할 빈도/가능성
  - **C (Controllability, 제어가능성)**: 운전자/시스템이 위험을 회피할 수 있는 정도
- 등급: **QM(품질관리만 필요, 안전등급 아님) → ASIL A → ASIL B → ASIL C → ASIL D(가장 엄격)**
  - ASIL D: 브레이크, 스티어링처럼 실패 시 즉각적 치명적 사고로 이어지는 영역
  - ASIL A: 상대적으로 위험도가 낮은 영역
- 등급이 높을수록: 더 엄격한 개발 프로세스, 더 강한 테스트 커버리지 요구(MC/DC 등), 더 엄격한 코딩 표준 준수, 더 많은 독립적 검증(예: 별도 검증팀) 요구.

### 3.2-1 MISRA의 Pass/Fail 과 ASIL의 등급은 같은 종류의 "결과"가 아니다

헷갈리기 쉬운 지점이라 명확히 구분한다.

- **MISRA**: 코드를 검사해서 나오는 **결과**다. 등급이 없고, 규칙별 **위반/통과(pass-fail)** 목록만 나온다. (예: "Rule 8.4 위반 5건")
- **ASIL**: 코드를 검사해서 나오는 결과가 **아니다**. 코드를 작성하기 전, 그 기능이 무엇을 하는지(용도/역할)를 보고 **HARA(위험분석)로 먼저 정해지는 "합격 기준(요구 등급)"** 이다. 정확히 말씀하신 대로 **"코드 용도에 따라 먼저 A~D 중 기준을 잡는" 것**.

즉 인과관계는 이렇다:

```
[기능의 용도/위험성] → (HARA로 판단) → [ASIL 등급 확정 = 요구되는 엄격도]
                                              ↓
                          "ASIL D면 MISRA 위반 0건이어야 한다" 같은 요구사항이 부과됨
                                              ↓
                      도구로 코드를 검사 → MISRA 위반 0건인지 pass/fail 확인
                                              ↓
                "이 코드가 부과된 ASIL D 요구수준을 만족했다"는 증거(evidence) 확보
```

도구가 "이 코드는 ASIL B다"라고 판정해주는 게 아니다. **ASIL은 이미 외부(위험분석)에서 정해져 있고, 도구는 그 정해진 기준을 코드가 실제로 만족(pass)했는지 확인하는 수단**일 뿐이다. 비유하면 ASIL = "합격선을 95점으로 정하는 것"(위험분석으로 결정), MISRA 검사 = "실제로 95점을 받았는지 채점하는 것"(도구로 확인) 관계.

### 3.3 그래픽 엔진과의 관계
자동차용 "인포테인먼트/클러스터/HUD용 그래픽 엔진"이라면 이게 직접적으로 적용된다.
- 보통 클러스터(계기판)에 표시되는 속도/경고등 같은 안전 관련 정보 렌더링 부분은 ASIL B~D로 분류되는 경우가 있고,
  단순 인포테인먼트(내비/미디어)는 QM 또는 ASIL A 수준으로 분류되는 경우가 많다.
- 동일 엔진 안에서도 **기능별로 ASIL 등급이 다르게 매겨질 수 있고(예: 계기판 렌더 vs 배경 애니메이션)**, 이걸 분리(decomposition/partitioning)해서 등급이 낮은 부분의 비용 부담을 줄이는 설계가 실무에서 흔함.
- 차량용이 아니라면(콘솔/PC 게임 엔진 등) ASIL은 적용 대상이 아니고, MISRA만 "신뢰성 향상 목적"으로 자율 채택하는 경우가 많음.

## 4. 검증 단계는 보통 이렇게 나뉜다

실제 안전 critical 개발에서 "검증(Verification)"은 한 가지 활동이 아니라 여러 단계의 조합이다. 도구 조사할 때 "이 도구가 이 중 어디를 커버하는지"를 기준으로 분류하면 헷갈리지 않는다.

1. **정적 분석 / 코딩 표준 준수 검사 (Static Analysis)**
   - MISRA, AUTOSAR C++14, CERT C/C++ 같은 규칙을 코드(소스 텍스트/AST) 수준에서 검사.
   - 컴파일 없이도 가능. 가장 먼저, 가장 많이 돌리는 검증.
2. **정적 분석 — 결함 탐지 (Defect/Bug Detection)**
   - MISRA처럼 "스타일/패턴" 규칙이 아니라, null pointer dereference, buffer overflow, use-after-free, race condition 같은 실제 버그를 찾는 분석.
   - 일부 도구는 MISRA 검사기와 결함 탐지기를 동시에 제공 (예: Polyspace, Coverity, PVS-Studio).
3. **정적 분석 — 수학적 증명 기반 (Formal/Abstract Interpretation)**
   - 추상해석(Abstract Interpretation) 등을 이용해 "이 코드에는 런타임 에러가 없다"를 수학적으로 증명하려는 강력한 분석.
   - 예: Polyspace Code Prover, Astrée, TrustInSoft. ASIL D처럼 최고 등급 요구 시 선호됨.
4. **동적 분석 / 런타임 검증**
   - 실제 실행하면서 ASan/UBSan/Valgrind 같은 도구로 메모리/UB 문제 탐지.
   - 그래픽 엔진은 GPU 드라이버/비동기 실행이 끼어 있어 이 영역이 특히 중요(레이스 컨디션, GPU-CPU 동기화 버그 등).
5. **테스트 커버리지 (Coverage)**
   - 단위 테스트가 코드를 얼마나 실행했는지. ASIL 등급이 높을수록 Statement/Branch/**MC/DC(Modified Condition/Decision Coverage)** 까지 요구.
6. **추적성 (Traceability) / 프로세스 검증**
   - 요구사항 → 설계 → 코드 → 테스트가 서로 연결되어 추적 가능한지. 도구라기보단 ALM(요구사항 관리) 영역(예: Polarion, DOORS)과 연계.
7. **인증/심사 (Certification, Assessment)**
   - 위 모든 산출물을 가지고 TÜV, Exida 같은 인증기관이 "이 도구/프로세스가 ISO 26262를 만족한다"고 평가.
   - 도구 자체가 "ISO 26262 Tool Qualification(TCL1~3, 도구 신뢰도 등급)"을 받았는지가 구매 시 중요 포인트가 됨 — 인증된 도구를 쓰면 별도 검증 부담이 줄어듦.

→ 다음 단계(도구 목록 조사)에서는 각 도구가 위 1~7 중 **어디를 커버하는지, MISRA C/C++ 버전 지원범위, ASIL Tool Qualification 인증 여부, 무료/유료**를 표로 정리하는 게 좋은 틀이 될 것.

## 5. 용어 미니 사전

| 용어 | 의미 |
|---|---|
| UB (Undefined Behavior) | 언어 표준이 동작을 정의하지 않은 코드 — MISRA가 가장 적극적으로 차단하려는 대상 |
| Deviation | MISRA 등 규칙 위반을 의도적으로 허용하고 문서화하는 절차 |
| HARA | Hazard Analysis and Risk Assessment, ASIL 산정 절차 |
| SOTIF (ISO 21448) | ISO 26262와 별개로 "오작동은 없지만 성능 한계로 발생하는 위험"을 다루는 표준 (예: 센서 인식 한계) — 자율주행 인지 쪽에서 자주 언급됨 |
| MC/DC | Modified Condition/Decision Coverage, 복잡한 조건문 테스트 커버리지 기준. ASIL D / DO-178C Level A 등에서 요구 |
| TCL (Tool Confidence Level) | ISO 26262-8에서 정의하는 "검증 도구 자체의 신뢰도 등급" (1~3) |
| AUTOSAR C++14 | MISRA C++와 유사한 또 다른 C++ 코딩 가이드라인(자동차 업계, C++14 기반). 실무에서 MISRA와 같이/대체로 언급됨 |
| SAST | Static Application Security Testing — 보안 취약점 관점의 정적분석. MISRA/안전과는 목적이 다르지만 같은 도구가 겸하는 경우 많음 |

## 6. 다음 조사 단계 (제안)

이 문서는 배경지식까지만 다룸. 이어서 조사할 내용:

1. 검증 도구 목록 (Polyspace, Coverity, Klocwork/Axivion, PVS-Studio, Cppcheck, clang-tidy, PC-lint Plus, Astrée, Parasoft C/C++test 등)
2. 각 도구의 MISRA C / MISRA C++(2008/2023) / AUTOSAR C++14 지원 범위
3. ASIL Tool Qualification(TCL) 인증 여부 및 인증 기관
4. 무료(오픈소스) vs 상용 라이선스 비용 구조
5. 그래픽 엔진 특성(템플릿, SIMD, 멀티스레딩, GPU API 바인딩 코드)과의 호환성/오탐(false positive) 수준
